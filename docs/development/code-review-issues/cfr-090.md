# CFR-090: HTTP remote commitish解決の一時directory名が競合し得る

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | medium |
| Type | correctness-risk |
| Area | HTTP remote view |
| Source | `crates/codefire-cli/src/view.rs:391` |

## Problem

HTTP remote commitish解決では、remote bundleをprocess IDとcommitish hash由来の一時directoryへ展開する経路がある。既存directoryを削除してから使う設計だと、同一process内の並行処理や近接した再入で競合・stale cleanupが起き得る。

## Why It Matters

remote show/diff/reviewはautomationが並行実行しやすい。deterministic temp pathを削除して再利用すると、片方の処理がもう片方のbundleを消す可能性がある。remote境界の読み取りは副作用が小さいほどよい。

## Failure Mode / Review Hypothesis

同じremote branchを並行してdiff/showすると、同じtemp pathを使い、片方が `remove_dir_all` 相当のcleanupを行う。もう片方のobject readが途中で失敗するか、古いbundleと混ざる。

## Code Evidence

- Primary source: `crates/codefire-cli/src/view.rs:391`
- Observed implementation fact: `resolve_commitish_any` handles local/remote commitish and creates temp object area for HTTP bundles.
- Related source: `crates/codefire-cli/src/main.rs:4044`
- Observed implementation fact: stable hash helper is available and deterministic temp naming has been used elsewhere.

## Recommended Fix

HTTP bundle展開には一意な tempdir guardを使い、既存directory削除に頼らない。lifetimeはguardで管理し、parallel-safeにする。bundle cacheが必要なら明示的cache moduleとlockを設ける。

## Implementation Notes

- First step: 同一remote diff/showをthreadで並行実行するunit/integration testを追加する。
- Boundary: remote cache導入は別設計。まず一時directory安全性だけを直す。

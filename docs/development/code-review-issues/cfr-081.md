# CFR-081: JSON失敗経路が共通envelopeを通らない

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | maintainability |
| Area | CLI JSON output |
| Source | `crates/codefire-cli/src/main.rs:121`, `crates/codefire-cli/src/main.rs:831` |

## Problem

`main()` は `run(args)` の失敗を `eprintln!("error: {error}")` で処理している。成功時のJSONは `automation::command_result_envelope` に寄せられているが、parse error、unsupported subcommand、commitish解決失敗、remote errorなどの失敗経路はglobal handlerでhuman textへ落ちる。

## Why It Matters

AI toolやCIは `--json` を指定していても失敗時だけtext parserを必要とする。dogfoodingでは `show --json`、`branch show --json`、`context --atom UNKNOWN --json` などで同じ問題が観測された。JSON success/failure symmetryはautomation契約の中核なので、個別commandの追加だけでは解決しない。

## Failure Mode / Review Hypothesis

`--json` を含むcommandがparse後に `CliError` を返すと、process exit codeは妥当でもstdout/stderr shapeが壊れる。外部自動化はdiagnostic kind、target、next_actionsを失い、再試行やissue記録を安定化できない。

## Code Evidence

- Primary source: `crates/codefire-cli/src/main.rs:121`
- Observed implementation fact: top-level error handler is text-only.
- Related source: `crates/codefire-cli/src/main.rs:831`
- Observed implementation fact: `CliError` has display and exit code, but not structured diagnostic conversion.

## Recommended Fix

`CliError` を `CommandDiagnostic` へ変換する共通APIを作り、top-level dispatchで「このcommandがJSON modeを要求していたか」を早期に保持する。JSON要求時の失敗は `codefire.command_result.v1` envelopeで `ok=false`、`exit_code`、diagnosticsを返す。

## Implementation Notes

- Priority: v0.9 contract hardeningの最初に扱う。
- First step: `codefire show main --json` 失敗/成功両方のJSON envelope regression testを追加する。
- Boundary: AI agent運用機能ではなく、CLI automation contractの改善として実装する。
- Related issues: CFB-057, CFB-058, CFB-059, CFB-060, CFB-062, CFR-095.

## Acceptance Criteria

- JSON対応commandで失敗時も `schema`, `command`, `ok=false`, `exit_code`, `diagnostics` が返る。
- global error text pathはJSON未指定時だけ使われる。
- parse error、usage error、repo error、remote errorの最低4分類がstructured diagnosticになる。

## Test Plan

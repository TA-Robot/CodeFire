# CFR-174: request-applyがMRで承認されたsource headを固定しない

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | critical |
| Type | correctness-risk / security-risk |
| Area | Remote merge request apply |
| Source | `crates/codefire-cli/src/remote.rs`, `crates/codefire-cli/src/http.rs`, `codefire` |

## Problem

file/HTTP/Pythonの`request-apply`はMRの`source_head`ではなく、apply時点のsource branch recordからheadを読み、
そのheadをtarget branchへ公開する。review後にsource branchがfast-forwardすると、MRに記録・承認されていない
commitまでapplyできる。

## Why It Matters

MRのapproval subjectと実際に公開されるcommitが一致しない。fast-forward ancestryは新しいcommitがreview済みである
証明ではなく、branch protectionとreview auditを迂回するcorrectness/security failureになる。

## Failure Mode / Review Hypothesis

1. feature head AからMRを作りapproveする。
2. feature branchをAの子Bへuploadする。
3. 同じMRをapplyする。
4. 現行実装はMRのAではなく現在のBをtargetへ公開する。

さらにHTTP applyはtarget branch lock取得後のhead再検証がなく、file uploadもbranch lock後のhead再検証がないため、
並行更新で同じsubject driftが拡大する。

## Code Evidence

- `remote.rs::apply_merge_request`はMRを読む一方、公開headを`load_remote_branch(&source)`のcurrent headから取る。
- `http.rs::handle_http_request_apply`も`http_remote_branch`のcurrent source headを使う。
- Python `cmd_request_apply`もcurrent source branchの`head`をbranch/MR postimageへ書く。
- CFR-165の独立read-only設計監査で3 runtimeの同型経路を確認した。

## Recommended Fix

MRのversioned immutable subjectとして`source_head`を扱い、applyはそのexact sealed commitだけをvalidate/copy/publishする。
MR、target branch、generation、idempotencyをCFR-165/ADR-017の一つのguardとdurable transactionへ束縛し、lock後に
MR identity/status/target preimageを再検証する。

## Implementation Notes

- Priority: CFR-165を閉じる前のsame-batch blocker。
- First step: approve後にsourceを進めてもtargetはMR source headだけへ進むcounterexampleを追加する。
- Boundary: semantic auto-mergeや最新headの暗黙再approvalは実装しない。
- Related issues: CFR-165、ADR-017、RVC-041/044/050/056。

## Acceptance Criteria

- file/HTTP/Python applyはMRに記録されたexact `source_head`だけを適用する。
- source branchが進んでも結果はreview subjectから変化せず、target/MR/resultが同じheadで一致する。
- review/apply、upload/applyの両interleavingはlock後のstale preimageをwrite前に拒否またはowner transactionへ収束する。
- malformed/changed MR subject、missing/unsealed reviewed headはbranch/MR/idempotencyを変更せずfail closedする。

## Test Plan

- approve A、source upload B、apply後target=A/MR applied_head=Aをfile/HTTP/Pythonで確認する。
- barrierでapplyのpre-lock read後にsource/target/MRを進め、post-lock revalidationとraw nonmutationを確認する。
- CFR-165の全phase recoveryでresult head、branch head、MR applied headの一致を確認する。

## Implemented Source Evidence

- File/HTTP/Rust/Python request-merge stores a versioned immutable subject and copies the complete
  source graph into target-local escrow while ordered gates are held.
- Every review binds the recomputed subject digest. Apply validates the effective approving review
  and consumes the MR `source_head` from target escrow; it does not read the current source branch.
- Apply journals generation, target branch, and MR so result head, branch head, `applied_head`, and
  subject head are identical across retry.
- File and HTTP regressions advance or remove the source after approval and still apply the exact
  approved head. Subject/review tampering and stale target paths preserve authority and fail closed.
- Independent final source review reported no remaining blocker.

## Close Evidence

- File and HTTP installed regressions keep target/MR/result at reviewed A after source advances to B
  or the source project is removed; both full runtime suites pass.
- Subject golden, source-removal escrow, subject/review tamper, stale target, and publication replay
  tests pass across Rust/Python. The CFR-165 fresh install, real probes, Algorithm Dogfood, and
  independent High review provide the shared lifecycle evidence.

## Retrospect

Ancestry and current branch state cannot substitute for review identity. Keeping the complete graph
in target escrow made review/apply both immutable and available after source removal without a lease.
No semantic auto-merge or implicit reapproval was introduced.

# CFR-135: storage largest object集計が全object情報を保持してからtruncateする

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | performance |
| Area | Storage report |
| Source | `crates/codefire-cli/src/storage.rs:471`, `crates/codefire-cli/src/storage.rs:491` |

## Problem

largest objects集計は全objectのmetadataをvectorに保持してsortした後にtruncateする。巨大repoではtop-Nだけ必要な処理に対してメモリ使用量が過大になる。

## Impact

storage reportは肥大化したrepoほど必要になるが、そのrepoでレポート自体が重くなる。

## Recommended Fix

固定サイズmin-heapでtop-Nを保持し、全entry vectorを作らない。全件が必要な場合は明示flagを用意する。

## Acceptance Criteria

- largest object集計のメモリ使用量がO(N)からO(K)になる。
- KはJSONに `largest_limit` として表示される。
- 既存出力順は保持される。

## Test Plan

- synthetic large object listでtop-Nが同じ結果になる単体テストを追加する。

## Fix

Largest object collection now goes through a bounded top-N helper. The implementation keeps only `LARGEST_OBJECT_LIMIT` entries sorted by bytes and object ID, instead of accumulating every object entry and truncating after a full sort.

The JSON result exposes `objects.largest_limit`.

## Verification

- `cargo test -p codefire-cli storage_`
- Full workspace checks in global burn-down verification.
- Existing storage object fixture verifies sorted largest output and the new `largest_limit` field.

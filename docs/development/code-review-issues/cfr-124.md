# CFR-124: manual fire作成がlock取得前の古い状態を元に実行される

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | correctness-risk |
| Area | Fire lifecycle |
| Source | `crates/codefire-cli/src/fire.rs:149`, `crates/codefire-cli/src/fire.rs:339` |

## Problem

manual fire追加処理は既存fire ledgerを読み、追加対象を組み立てた後にrepo lockを取得する。lock取得後にledgerを再読込・再検証しない。

## Impact

並行操作があると古い状態に基づいてdisplay IDやfire UIDを生成し、重複や順序ずれが発生し得る。

## Code Evidence

- `crates/codefire-cli/src/fire.rs:149`: `build_manual_fires` がlock前に呼ばれる。
- `crates/codefire-cli/src/fire.rs:339`: display IDが既存ledger長に依存する。

## Recommended Fix

非dry-runではlock取得後にledgerを再読込し、追加対象を再計算する。dry-run planにはlock後再検証が必要であることを明示する。

## Acceptance Criteria

- 並行manual fire追加でdisplay ID重複が起きない。
- lock前後で状態が変わった場合に再計算される。
- dry-run planにstale read riskが残らない。

## Test Plan

- 同一repoで並行 `fire open` を実行するintegration testを追加する。

## Resolution

- Non-dry-run manual fire creation now acquires the repository lock before reloading active state and rebuilding fire records.
- The operation plan reports `requires_lock_revalidation` so dry-run consumers know apply will re-read state under lock.
- Regression: `manual_fire_and_batch_validate_before_writing_fires`; full `cargo test --workspace`.

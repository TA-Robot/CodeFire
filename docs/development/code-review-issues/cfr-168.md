# CFR-168: graph/object/HTTP workにdecision-equivalent budgetがない

## Summary

| Field | Value |
|---|---|
| Status | investigating |
| Severity | high |
| Type | performance-risk / resource-safety |
| Area | Graph evaluation / Validation cache / HTTP output / Metrics |
| Source | RVC-014/015/029/042/047/048/058 |

## Problem

required-link lookupの局所indexやStore validation cacheはあるが、branch listはheadごとにcache scopeを再作成し、
ancestry/signature historyは全map/recursive traversal、HTTP bundle/JSON responseは全object materializationを行う。
files、bytes、objects、edges、validation hits、queue depth等のcorrectness work counterとcommand別budgetがないため、
bounded outputでも内部work/memory amplificationを検出・制御できない。

## Root Cause and Deduplication

既存CFR-024/025/026/028/030/042/076/088/089/128/134-137/147-149/156/157は局所上限を追加した。
残差は「同じsemantic resultを守りながら全phaseのworkを測定・制限する」共通budget/evaluator contractである。

## Required Fix

- graph direction/closure/cycle semanticsとiterative reference evaluator。
- command-scoped validated graph/cacheをbranch/storage/doctor/ancestryで共有する。
- request/response/object graphをbyte/count/depth/time/memory別にstream/pageし、snapshot tokenを束縛する。
- stable work countersとbudget-exceeded typed outcomeをmetrics/diagnosticsへ出す。

## Acceptance Criteria

- selected operationsの時間/メモリorderをdocsとscale fixturesで固定し、recursive stack growthを除く。
- output limitに達する前の内部read/validation/materializationもbudgetで停止する。
- cache有無でdiagnostic/result/orderが同一になり、store subject変更時はreuseしない。
- x10 fixtureでwork counterがaccepted bound内に収まり、budget超過はpartial successでなく明示failure/continuationになる。

## Test Plan

- graph depth/fanout/cycle、many-head shared DAG、large HTTP bundle、signature history scale fixtures。
- cache equivalence/invalidations、stream/page snapshot replay。
- work counter golden and asymptotic assertions。

## Characterization Evidence

- `codefire-core::build_scan_result_with_options`はchanged Atomごとに`adjacent_atoms`を呼び、同関数が
  Trace Link全件を再走査するため、現状の支配workは`changed_atoms × links`である。
- `remote::is_ancestor_in_objects`は一件のancestor判定にも`ancestor_distances`で全到達mapを作る。
  `signatures::verify_commit_policy_recursive`はvisited setを持つが、深い履歴をprocess call stackへ積む。
- Storeの`validate_sealed_commit_inner`もparentごとのrecursive callで、command-scoped cacheは既にobject-root
  identityへbindされる一方、深い履歴のstack budgetとread/validation counterを公開しない。
- `remote::collect_object_records`はreachable recordを全件`Value`へmaterializeしてからsortする。
  HTTP bundleはさらにresponse全体を`Vec<u8>`へserializeし、server生成後にclientの16 MiB上限で拒否され得る。
- HTTP uploadはincoming record適用前にexisting remote object store全体をtemp directoryへcopyするため、tiny deltaでも
  unreachable store sizeに比例したI/O/tempを使い、request body limitでは防げない。
- `metrics.rs`はresult countとelapsed timeを持つ一方、file/object read、bytes hashed、graph node/edge、
  validation/memo workを持たず、同値な高速化とvalidation省略を区別できない。
- current HTTP error transportはserverで`error`/`exit_code`へ畳み、client `RemoteDiagnostic`も
  status/kind/message/exitだけを保持するため、budgetのprofile/dimension/observed/limit/phaseを失う。
- Python fallbackはresponse/object collectionとrequired-link/ancestry/signature traversalがunboundedまたは
  recursiveで、common ancestorもRustのgeneration tie-breakを共有しないため、同じprofile/golden corpusが必要である。
- ADR-020は独立adversarial reviewで`ACCEPT_FOR_IMPLEMENTATION`となった。command snapshotは保持済み
  parsed valueをmemoに使い、成功/ mutation preflight完了直前に全memoized documentをdigest/sizeで一回
  再検証する。deadlineはdeterministic ledgerと分離し、publication開始後はdurable reducerの完了/回復を
  優先する。Rust common-ancestor semanticsを正としたPython tie-break correctionも同ADRで凍結した。

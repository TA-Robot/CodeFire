## Problem

batch extinguishのresult dataはoperation plan寄りで、適用後に何件解消したか、どのfire IDが更新されたか、active open fire countがどう変わったかを直接読み取りにくい。

## Why It Matters

AI toolはbatch後に次のverify/scanへ進むかを判断する。成功結果にapplied summaryがないと、追加でstatus/scan/contextを呼ぶ必要があり、操作回数とログが増える。

## Failure Mode / Review Hypothesis

batch commandが成功しても、toolは「全件適用された」「部分適用なし」「open firesが残っている」をresultだけで判断できない。結果として次action生成が保守的になり、無駄なscanを繰り返す。

## Code Evidence

- Primary source: `crates/codefire-cli/src/batch.rs:223`
- Observed implementation fact: operation plan builder is central, success result summaryとは別の構造が弱い。
- Related source: `crates/codefire-cli/src/main.rs:3325`
- Observed implementation fact: single extinguish result has richer per-fire result context.

## Recommended Fix

`ExtinguishBatchResult` を導入し、`applied_count`、`fire_ids`、`resolution_ids`、`remaining_open_fire_count`、`active_state` を返す。dry-run planとは別schemaにする。

## Implementation Notes

- Priority: medium。
- First step: batch success JSONのcontract testを追加する。
- Boundary: text output変更は最小限に留める。
- Related issues: CFR-100, CFR-101.

## Acceptance Criteria

- batch success JSONだけで適用件数と対象fireが分かる。
- dry-run dataとapply result dataが区別される。
- next_actionsがremaining stateに基づく。

## Fix

- `extinguish --batch --json` now returns a `codefire_extinguish_batch_result` data object instead of only wrapping a generic operation plan.
- The result includes `dry_run`, `item_count`, `applied_count`, bounded `fire_ids`, bounded `resolution_uids`, `remaining_open_fire_count`, and the bounded plan.
- Dry-run and apply are distinguished by `dry_run` / `applied_count`, while text output remains minimal.
- Existing two-fire batch tests now assert `applied_count`, target IDs, resolution IDs, remaining open fire count, and data type.

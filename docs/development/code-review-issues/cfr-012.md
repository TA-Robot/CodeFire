# CFR-012: object書き込み完了前クラッシュの検出粒度が弱い

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | correctness-risk |
| Area | Object store |
| Source | `crates/codefire-store/src/lib.rs:222` |

## Problem

object fileは `create_new` で直接最終pathへ書いている。途中クラッシュ時、最終名の不完全JSONが残る。

## Why It Matters

次回同一object保存時に既存fileとして読みに行き、JSON errorで復旧しにくくなる。

## Failure Mode / Review Hypothesis

通常ケースでは動いても、境界条件や並行実行でCodeFireの整合性表示・保存結果がずれる可能性がある。次回同一object保存時に既存fileとして読みに行き、JSON errorで復旧しにくくなる。

## Code Evidence

- Primary source: `crates/codefire-store/src/lib.rs:222`
- Observed implementation fact: object fileは `create_new` で直接最終pathへ書いている。途中クラッシュ時、最終名の不完全JSONが残る。

## Recommended Fix

objectもtmp fileへ完全書き込み、validate後renameする。破損object検出時のrepair導線も用意する。

## Implementation Notes

- Priority: 機能追加の前後で一緒に片付ける。単独修正でも価値はあるが、関連領域の改修時にまとめると効率がよい。
- First step: 小さな再現fixtureを作って、現状の挙動を固定してから修正する。
- Boundary: AI agent運用機能やmarketplaceをCodeFire本体へ入れず、整合性管理・履歴封印・自動化tool向けI/Oの改善として扱う。
- Related issues: [CFR-010](cfr-010.md), [CFR-011](cfr-011.md), [CFR-013](cfr-013.md), [CFR-014](cfr-014.md), [CFR-015](cfr-015.md), [CFR-016](cfr-016.md)

## Acceptance Criteria

- 不完全object fileをdoctorが検出し、対象pathを報告する。
- 正常保存はatomic rename経由になる。

## Test Plan

- truncated object fixtureのdoctor/store test。

## v0.7 Resolution

- object storeはfinal pathへ直接書かず、同一directoryの一意temp fileへ完全書き込み、`sync_all`、record validation後にpublishする。
- publishはhard linkでfinal pathを作るため、同時writerが先に同じobjectを保存した場合は既存recordをvalidateして再利用する。
- doctorは既存の `invalid_object_record` / `object_integrity_error` でtruncatedまたはtampered final objectを検出する。

# CFR-100: batch extinguishが検証と適用を単一transactionで守れていない

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | correctness-risk |
| Area | Batch extinguish |
| Source | `crates/codefire-cli/src/batch.rs:124` |

## Problem

`run_extinguish_batch` は全itemをdry-run的に検証した後、別ループで各itemを `run_extinguish` する。検証と適用の間にactive fires/resolutionsが変化した場合、all-or-nothing保証が弱くなる。

## Why It Matters

batch extinguishは大量fireをまとめて解消する重要操作である。途中で状態が変わると、検証済みだったitemが古くなり、部分適用やstale basisを生む可能性がある。AI toolはbatchを多用するのでtransaction境界が重要になる。

## Failure Mode / Review Hypothesis

別processがfire ledgerを更新した後にbatch applyが進む。前半itemは適用済み、後半itemで失敗し、batch全体のatomicityが壊れる。あるいは検証時と異なるbasisでresolutionが保存される。

## Code Evidence

- Primary source: `crates/codefire-cli/src/batch.rs:124`
- Observed implementation fact: batch extinguish validates items first and then applies items in a separate loop.
- Related source: `crates/codefire-cli/src/main.rs:3325`
- Observed implementation fact: single extinguish runner owns mutation and idempotency.

## Recommended Fix

batch extinguish専用のtransaction runnerを作り、active lock取得後に全itemを再検証し、ledgerを一度だけ読み書きする。single runnerのロジックはpure helperへ分離して再利用する。

## Implementation Notes

- Priority: high。
- First step: concurrent modification simulation testを追加する。
- Boundary: lock scopeは広げすぎず、active state mutationに必要な範囲に限定する。
- Related issues: CFR-101, CFB-050.

## Acceptance Criteria

- batch apply中にactive stateが変わった場合は全体が失敗し、部分writeしない。
- resolution basisはlock後の最新stateから作られる。
- batch resultにapplied countとskipped/failed diagnosticsが出る。

## Test Plan

- active firesを検証後に変更するfixtureまたはhook付きunit testを追加する。
- existing batch validation testsを維持する。

# CFR-088: patch exportがfile contentを無制限にbase64化し得る

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | performance |
| Area | Patch export |
| Source | `crates/codefire-cli/src/view.rs:282` |

## Problem

`patch_export_with_options` は変更fileのcontentをpatch JSONへbase64として含める設計である。巨大fileや大量fileに対する出力サイズ、メモリ使用量、stdout量の上限が明確でない。

## Why It Matters

patch exportは外部toolへの受け渡しで使われるため、大きなrepoで無制限payloadを作るとメモリ圧迫、terminal/CI log肥大化、tool側のparse失敗を招く。CodeFireは大規模repoで計算量とメモリ使用量に厳しくあるべきというAGENTS方針にも反する。

## Failure Mode / Review Hypothesis

大きなbinaryや生成物がmanifest差分に含まれると、export commandが全contentを読み込み、base64で約1.33倍に膨らんだJSONを作る。stdout出力ならさらにログ保管が肥大化する。

## Code Evidence

- Primary source: `crates/codefire-cli/src/view.rs:282`
- Observed implementation fact: patch export builds a JSON patch payload including file entries.
- Related source: `crates/codefire-cli/src/view.rs:466`
- Observed implementation fact: manifest content loading is full-content map oriented.

## Recommended Fix

patch exportに `--max-bytes`、default payload cap、file count cap、binary omission policy、artifact reference modeを導入する。巨大contentはhash/size/path summaryにし、明示flagなしではpayloadへ入れない。

## Implementation Notes

- Priority: high。memory discipline issue。
- First step: large file fixtureでexportがbounded omissionを返すtestを追加する。
- Boundary: Git互換patchを目指さず、CodeFire patch formatの安全性を優先する。
- Related issues: CFR-089, CFR-087.

## Acceptance Criteria

- default patch exportは設定されたbyte capを超えない。
- omitted fileはhash、size、reason、必要なnext actionをmetadataに出す。
- `--include-large-files` のような明示flagがない限り巨大base64 payloadを作らない。

## Test Plan

- large binary/text fixtureでpatch exportのpayload capとomission metadataを検証する。
- stdout/file output双方のサイズ上限を確認する。

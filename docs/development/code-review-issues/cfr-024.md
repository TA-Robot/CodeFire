# CFR-024: required link計算がAtomごと全link走査になっている

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | performance |
| Area | Required links |
| Source | `crates/codefire-core/src/lib.rs:745` |

## Problem

各Atomの各ruleごとに `trace_graph.links.iter()` をfilter/countしている。

## Why It Matters

Atom数A、rule数R、link数Lに対して概ね O(A*R*L) になり、大規模repoで重くなる。

## Failure Mode / Review Hypothesis

入力規模が増えたときに処理時間またはメモリ使用量が急増する可能性がある。Atom数A、rule数R、link数Lに対して概ね O(A*R*L) になり、大規模repoで重くなる。

## Code Evidence

- Primary source: `crates/codefire-core/src/lib.rs:745`
- Observed implementation fact: 各Atomの各ruleごとに `trace_graph.links.iter()` をfilter/countしている。

## Recommended Fix

`(from, type, target_kind)` のindexを事前構築して O(A*R + L) に近づける。

## Implementation Notes

- Priority: 大規模repoや実験artifactが増える前に上限設計を入れる。
- First step: 最悪ケースの入力サイズを決め、修正前後の計算量と実測を比較する。
- Boundary: AI agent運用機能やmarketplaceをCodeFire本体へ入れず、整合性管理・履歴封印・自動化tool向けI/Oの改善として扱う。
- Related issues: none identified in this review batch.

## Acceptance Criteria

- required link checkがlink indexを使う。
- 大量Atom/link fixtureで性能回帰を測る。
- `required_link_missing` はAtom kind mapと `(from, type, target_kind)` link count indexを事前構築し、link走査を1回にする。
- 計算量は概ね `O(A + L + A*R)` になり、従来の `O(A*R*L)` 全link再走査を避ける。

# CodeFire v0.6 Rust Rewrite Plan

この計画は、現在のPython MVPを仕様oracleとして残しつつ、v0.6でRust実装へ移行するための開発計画である。

v0.6の目的は「速い同等品」ではなく、CodeFireを実プロジェクト管理に使い続けられる品質へ上げること。特にdogfoodingで見えたUX、診断ノイズ、性能可観測性、object store肥大化リスクを、Rust再設計の初期制約として扱う。

## Goals

- Rustで再実装した `codefire` CLIを提供する。
- 既存Python版のrepository、object store、sealed commit、trace/fire/verify/remote互換性を維持する。
- 主要操作を高速化し、phase別metricsを標準で観測できるようにする。
- fire解消、verify診断、large artifact運用を高機能化する。
- Rust crate分割により、CLI、core model、storage、indexer、remote server、policy engineを独立してテストできるようにする。

## Non-Goals

- v0.6でGUIを完成させること。
- 既存object formatを破壊的に変更すること。
- Git互換の全機能を目指すこと。
- ML実験artifact本体をCodeFire object storeに無制限保存すること。

## Compatibility Policy

v0.6 Rust版は、既存Python版で作成したrepositoryを読み書きできることを必須にする。

- object ID、canonical JSON、branch head、open registry、sealed commit validationは互換。
- Rust版で作ったcommitをPython版が最低限 `doctor` / `show` できる状態を維持する。
- format変更が必要な場合は、object payloadにversioned extensionを追加し、既存fieldの意味を変えない。
- Python版はv0.6期間中、reference implementation / migration checkerとして残す。

## Rust Workspace

想定workspace:

```text
crates/
  codefire-cli/          CLI entrypoint, shell completion, human output
  codefire-core/         Atom, TraceGraph, Fire, Resolution, Verification domain model
  codefire-store/        canonical JSON, object IDs, immutable object store, GC
  codefire-index/        Markdown/code/OpenAPI/SQL extractors
  codefire-policy/       required links, commit policy, verification planning
  codefire-remote/       file/http/https remote protocol, auth, signatures
  codefire-server/       hosted/server-side verification boundary
  codefire-testkit/      fixtures, parity harness, golden repository helpers
```

依存方針:

- CLI: `clap`
- serialization: `serde`, `serde_json`
- diagnostics: `miette` または `anyhow` + structured error enum
- hashing/signature: vetted crates only; object hash algorithmは既存仕様に合わせる
- async server: `tokio` + `axum` はremote serverが必要になった段階で導入する
- YAML: `serde_yaml` か `yaml-rust2` を比較し、既存limited YAMLとの差分を明示する

## High-Functionality Themes

### 1. Extinguish UX

Dogfooding issue: CFB-005.

v0.6 targets:

- `codefire extinguish --interactive`
- `codefire extinguish --batch fires.yaml`
- 複数fireを同じrationale/evidenceで解消する `--all-matching`
- 直近verification/test commandの結果をevidence候補として提示
- editor連携: `$EDITOR` でrationale/evidence draftを編集

### 2. Verify Diagnostics

Dogfooding issue: CFB-006.

v0.6 targets:

- `codefire verify --details --blocking-only`
- diagnostics severity: blocker / warning / info
- missing linksをkind別、source file別、policy rule別にgrouping
- next action hint: `add link`, `extinguish`, `refresh`, `deduplicate atom`
- machine-readable `--json` output

### 3. Performance Observability

Dogfooding issue: CFB-007.

v0.6 targets:

- `codefire perf status|scan|verify`
- `--metrics` flag for status/scan/verify
- phase timing: config parse, index, trace graph, fire generation, policy checks, verification commands, object load/store
- Atom count, link count, fire count, object count, object bytes
- slow phase warnings and cache hit/miss reporting

### 4. Storage and Artifact Management

Dogfooding issue: CFB-008.

v0.6 targets:

- `codefire storage report`
- object store size by type and generation
- large artifact warning threshold
- external artifact references:

```yaml
artifacts:
  mode: external
  roots:
    - name: local-runs
      path: /data/codefire-runs
```

- content hash for external artifacts without copying payload into `.codefire/objects`
- retention policy for active/recent sealed commits and remote generations

### 5. Indexer Reliability

v0.6 targets:

- tree-sitter-based optional extractors for common languages
- fallback lightweight extractors for no-dependency mode
- extractor diagnostics per file
- stable derived Atom IDs with owner/context namespace
- incremental scan cache keyed by file path, mtime, size, and content hash

### 6. Policy Engine

v0.6 targets:

- policy evaluation as structured rule results
- rule IDs and user-facing remediation text
- profile support:

```yaml
profiles:
  early_spec:
    require_trace_completeness: false
  release:
    require_trace_completeness: true
```

- per-branch and per-remote policy overlays

### 7. Remote and Server Hardening

v0.6 targets:

- Rust server implementation with strict request validation
- request/commit signature verification shared between CLI and server crates
- server-side verification sandbox abstraction
- audit log schema stabilization
- remote GC and retention metrics

### 8. Migration Tooling

v0.6 targets:

- `codefire migrate check`
- `codefire migrate dry-run`
- Python-created repo compatibility fixtures
- Rust-created repo compatibility fixtures
- golden object hash tests

## Milestones

|---|---|---|---|

## Testing Strategy

Test layers:

- unit tests per crate
- golden canonical JSON/object ID tests
- repository fixture compatibility tests
- Python-vs-Rust parity tests for command outputs and object graph
- end-to-end local demo
- remote protocol E2E
- corruption/doctor tests
- performance smoke tests with synthetic large Atom graph

Minimum v0.6 release checks:

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
python3 -m unittest discover -s tests -v
./demo.sh
codefire migrate check fixtures/python-v0.2-repo
```

## Migration Sequence

1. Add Rust workspace without changing installed `codefire`.
2. Build `codefire-rs` binary and run it only in tests.
3. Add parity fixtures generated by current Python CLI.
4. Make Rust `doctor`, `status`, `show` read existing repositories.
5. Implement local write path.
6. Run dogfooding with Rust binary on a copied repository.
7. Switch installer to install Rust binary as default.
8. Keep Python CLI as `codefire-py` until at least one stable release after v0.6.

## Risks

- canonical JSON incompatibility can corrupt object identity. Mitigation: golden tests before any write path.
- YAML parser behavior may drift from current limited subset. Mitigation: compatibility fixtures and explicit migration diagnostics.
- Rust rewrite can stall feature work. Mitigation: milestones preserve Python fallback until Rust reaches parity.
- tree-sitter dependencies can complicate packaging. Mitigation: optional feature flags and fallback extractors.
- external artifact refs can weaken reproducibility. Mitigation: store artifact hash, size, URI, timestamp, and retention policy in sealed objects.

## Open Decisions

- Use `serde_yaml` compatibility mode or keep a strict limited YAML parser.
- Use tree-sitter as default or optional extractor feature.
- Whether `codefire perf` is a top-level command or `--metrics` on existing commands only.
- How long to keep Python fallback after Rust v0.6 becomes default.
- Whether to introduce a new object type for external artifact references in v0.6 or only policy/docs first.

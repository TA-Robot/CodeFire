# CodeFire 立て直しと契約枠内マルチエージェント開発の提案

Status: decision-candidate; not an execution board

Owner: CodeFire product owner / orchestrator

Updated: 2026-09-05

Update trigger: 方針採用、契約プラン確認、初回実測、重大な反証。

対象は CodeFire 本体。開発基盤は本体改善に必要な範囲で扱う。ユーザーは Codex / Claude / Grok を契約済みで、**従量課金は禁止**。API料金、追加クレジット、超過課金を使う計画にはしない。

これは依頼された再計画の検討結果であり、既存の実行ボードを自動的に置き換えない。採用時は本書を別の現行計画として残さず、[milestones](../milestones.md)、[roadmap](../strategy/modernization-roadmap.md)、[routing policy](../ai/provider-routing-policy.md)へ必要事項を移す。今回、モデル呼び出しを伴う外部CLIの試運転、課金設定変更、製品コード変更は行っていない。

## 推奨する方向

「誰が何に困り、CodeFireのどの変更で改善したか」を一つずつ実証する。Codexが優先順位と統合を持ち、Fable 5.1を難しい設計・根本修正・重要レビューに、Grok 4.6を境界の明確な実装・再現・独立検証に配分する。すべて契約枠への包含が確認できた経路で実行する。

最適化対象は、週あたりの採用済み改善、利用者の介入時間、回帰率、契約枠消費。エージェント数、コミット数、完了宣言数は成果指標にしない。以下の人数や閾値は初期仮説であり、最適性が実測された値ではない。

## Fable 5.1 / Grok 4.6 の比較

2026-09-05参照。最も直接比較しやすい公表結果は同じCursorBench 3.2上のものだった。

| モデル・推論設定 | スコア | 平均cost/task（参考値） | Steps |
|---|---:|---:|---:|
| Fable 5.1 Max | 73.4% | $9.64 | 70 |
| Fable 5.1 Extra High | 72.8% | $6.96 | 55 |
| Fable 5.1 High | 69.4% | $4.80 | 44 |
| Grok 4.6 Extra High | 70.8% | $2.81 | 46 |
| Grok 4.6 High | 69.9% | $2.34 | 39 |
| Grok 4.6 Medium | 67.1% | $1.28 | 29 |

出典: [Cursorによる評価](https://cursor.com/evals)。costは各試行のtoken量へ公表単価を適用した値で、CodeFireの実費、契約枠の消費率、成功した仕事1件の費用ではない。小さい得点差には分散があり、統計的な優越を断定しない。Cursorの実行環境での比較であり、Claude Code / Grok Buildへそのまま移せる保証はない。

この表からの推論として、Grok Highを通常作業の出発点、Fable Extra Highを難しい設計・検証の候補とする。Fable MaxのExtra Highに対する増分は0.6ポイント、参考costは約39%増なので、全作業をMax固定する根拠は弱い。高リスクの設計判断や、他設定で反例を解消できない場合にMaxを使う。通常タスクでも失敗・手戻りが多ければ最初からFableへ配分する。

別の公表結果として、Fable 5.1はTerminal-Bench 4.0で55.8%、GDPval-AA v2で1853。Grok 4.6 HighはTerminal-Bench 3.0で26%、DeepSWE 1.1で65.9%、GDPval-AA v2で1753。[Anthropic発表](https://www.anthropic.com/claude-fable-and-mythos-5-1)、[xAI発表](https://x.ai/news/grok-4-6)。Terminal-Benchは版が異なるため比較不可。GDPvalも発表時期・測定条件が揃わず、選定の補助に留める。Grok発表内のFable比較対象は5であり、5.1ではない。

参考API単価は100万tokenあたり、Fable 5.1が入力$10・出力$50・cache read $0.25、Grok 4.6が標準帯の入力$2・出力$6・cache read $0.50。[Claudeモデル仕様](https://platform.claude.com/docs/en/models/fable-5-1/overview)、[Grokモデル仕様](https://docs.x.ai/developers/models/grok-4.6)。Grokには200K超の入力に価格段階がある。これらを契約枠へ換算せず、従量課金の実行計画も作らない。

## 従量課金ゼロの運用

固定費は既存の3契約の合計、追加の従量支出上限は0。プランの具体的名称と残量は未確認なので、月間処理件数や24時間連続稼働は約束しない。

| サービス | 公式に確認した制約 | 今回の扱い |
|---|---|---|
| Claude | Max / Premium seatではFableに週枠の最大50%を利用可能。Pro / Standard seatではFableはusage creditsで動く | Fableの契約内包含を確認してから使う。対象外なら、その契約に含まれるClaudeモデルか他社の契約内モデルへ切替 |
| Grok | Build等で週の利用プールを共有。枠切れ後は追加クレジットやAuto Top Upという経路がある | 契約認証でBuildを使い、追加クレジット消費・自動購入・API超過への切替を禁止 |
| Codex | ローカル/クラウドで枠を共有し、週制限もあり得る。API key経路は従量課金 | ChatGPT契約の認証経路で使い、購入クレジット・API認証への切替を禁止 |

出典: [ClaudeのFable契約条件](https://support.claude.com/en/articles/15424964-claude-fable-models-on-your-plan)、[Grok利用枠FAQ](https://docs.x.ai/grok/faq)、[Codex公式料金・利用枠](https://learn.chatgpt.com/docs/pricing)。Fable用50%は追加枠ではなく週枠の内数。

実行基盤には以下を小さく追加する案とする。

- 公式CLIの契約認証だけを許可。worker起動環境・設定にAPI課金、クラウド課金、別gatewayへの経路が混在していれば、そのlaneは起動前に止める。秘密値は記録しない。
- アカウント側の追加利用・自動購入設定を確認する。環境変数を外すだけでは既存設定経由の課金を防げない。料金フラグを0にするだけでも十分ではない。
- 課金経路やモデルの契約内包含が確認不能なら `billing-unverified` としてそのlaneを止める。CLIの存在、ログイン成功、APIのmodel catalogだけでは証明しない。
- 枠切れは `quota-paused`。branch/head、未コミット差分、試験結果、次の一手を保存する。許可済みの別契約枠へ仕事を移すかリセットを待ち、有料fallbackや同じ要求の再試行ループを行わない。
- 残量取得の公式な手段がなければ、利用画面から時刻付きで手動記録する。推定token単価を残量の代わりにしない。起動判定用記録は短い有効期限を持たせ、期限切れは更新待ち。
- 自動停止を検証できるまで無人の長時間運転を始めない。偽CLIで「API認証混入」「枠切れ」「残量不明」「有料fallback要求」を試験する。

初期配分は各サービスの使える枠の70%を予定作業、20%を修正・統合、10%を予備として留保する案。Fable固有枠があれば両方の上限を守る。枠の増減・残量・更新時刻に応じて調整し、この割合を公式仕様とは扱わない。

## 推奨する体制

| 役割 | 初期担当 | 責務 |
|---|---|---|
| 製品責任者 | ユーザー | 解く問題・優先順位・実利用での価値判断 |
| 指揮・統合 | Codex 1セッション | 受入条件、依存関係、配分、統合候補、次の判断を一元化 |
| 設計・難しい修正 | Fable 5.1 1セッション、契約内で利用できる場合 | 永続化・identity・復旧・状態遷移、複数moduleに跨る原因の調査 |
| 通常実装・再現 | Grok 4.6 1–2セッション | 具体的な利用経路、限定修正、再現fixture、独立した小変更 |
| 独立レビュー | 実装者と別セッション、可能なら別family | exact diffと要件から反例を探す。合意形成の会議にしない |
| 検証・記録 | shell / Rust / Pythonの既存ツール | テスト、差分・head照合、ログ収集、停止条件。LLMを監視の常時ループに使わない |

役割は常駐人数ではない。開始時は **Codex 1 + worker 2**。レビューを含め常時3–4セッションを目安にし、枠・CPU/RAM・独立した作業が揃うときだけ **Codex 1 + Claude 2 + Grok 2** を上限候補にする。レビュー待ちが2件以上なら新規実装を止め、先に統合する。並列数を増やす実験は、週あたり採用数が増え、回帰と人手が悪化しない場合に採用する。

現行の「Codexは指揮だけ」は初期移行で維持できるが、永久の能力制限とはしない。契約内のCodexを実装にも使う代替はCodeFireの実測後に判断し、変更する場合はAGENTS、policy、JSON、runtime設定、shellを一緒に改める。現在の `gpt-5.6-sol` 固定も能力評価と契約利用可能性に基づいて再検討する。旧pinを残したまま別モデルが走る状態は許容しない。

worktreeを分けても同じ論理契約を同時に変更すれば競合する。write setに加えて、変更するAPI・schema・共有型のownerを一人にする。`main.rs` やStoreの大きなファイルに触る修正は直列化し、独立fixtureや別moduleの仕事を並列にする。依存の強い実装を人数に合わせて分割しない。

各workerは `/workspace/project` のconfigured workspace内で動かす。基盤修正のworkerは基盤側workspaceとして明示的に別管理する。Grok backendがない間は、指揮役が作成した対象内worktreeで公式Grok CLIを単独運用し、既存schedulerがGrokを隔離・制限しているとは記録しない。

## 再計画：次の5段階

既存のエコシステム5段階は削除せず後段へ保留し、進出条件を「反復利用が確認でき、外部連携要求が実際に生じること」にする案。`narrow` という過去実験結果は保持する。その後の改善を新しい仮説・新しい版の実験として開始できるようにする。過去の凍結条件は、新しい開発まで永久に禁止する条件にしない。

| 順番 | 得たい成果 | 完了条件 |
|---|---|---|
| R1: 変更できる基準点 | 現在HEADを再ビルドして改善できる | cleanな隔離checkout、明示したtoolchain、Rustのfmt/clippy/test、CLI smoke、source/binary identityを記録。契約内起動と停止を確認 |
| R2: 一つの実用経路 | 要求変更→不整合の把握→修正→検証→seal→再確認/復旧が説明なしで辿れる | isolated dogfoodで成功・拒否・復旧を実測。sealの対象外・証明しないことを表示。観測された最上位の摩擦を修正 |
| R3: 回帰を防いで速く直す | 小変更が短く検証・統合できる | 高リスク不変条件の反例fixture、必要な性能の基準値、触るmoduleの境界整理、統合候補の自動検証 |
| R4: 実利用の反復 | 別の現実の変更でも使う理由がある | まず2–3人/利用環境で初回試用し、少なくとも一人が別の変更で再利用。介入・誤解・解決時間を記録。これは市場検証完了とは呼ばない |
| R5: 配れる限定版 | 利用者が導入・更新・復旧できる | 対応環境・既知制約・version/権利・install/rollbackを揃える。外部公開の判断は成果物が揃ってから行う |

R4の利用者候補選定や課題確認はR1から並行してよいが、連絡の送信はユーザーの明示指示がある場合のみ。人間の参加がない場合はR2/R3で製品改善を続け、AI dogfoodを人間の採用に読み替えない。

R1は立て直し時に一度行う広い基準検査。毎朝全ての過去テスト・文書検査をやり直す運用にはしない。以後は変更に適したfocused testから始め、Rust変更の引渡し前に既定のfmt/clippy/workspace testを実施する。基盤を変更したときは基盤AGENTSの全backend確認を使う。既存テストの失敗を「範囲外」の一言で成功に変えない。

性能修正は、ユーザー経路の待ち時間・CPU・メモリ・object read/hash数を測ってから行う。代表的な小/中/大repository、cold/warm、共有祖先、破損例を使い、性能改善後も拒否・診断が同じであることを確認する。初期値がないうちに根拠のないミリ秒SLOを約束しない。

## 1サイクルの実施方法

```mermaid
flowchart LR
    A[利用で観測した問題] --> B[再現と受入条件]
    B --> C[独立した実装を並列化]
    C --> D[focused testと独立レビュー]
    D --> E[統合候補の検証とinstall]
    E --> F[実タスクで利用]
    F --> G[価値と摩擦を測定]
    G --> A
```

1. 指揮役が一つの利用者成果を選ぶ。1cycleは1–3稼働日の大きさを目安とし、完了条件で閉じる。
2. 一つのtask packetへ目的、再現、受入条件、base HEAD、write/contract set、検証コマンド、禁止課金、担当をまとめる。独立したpacketは同時に進める。
3. workerは小さな変更を作り、同じHEADに対する試験結果を返す。連続2回の無進展なら再現の見直し・担当交代・分割を行い、同じpromptを回し続けない。
4. reviewerは実装者の自己評価に先導されず、要件・差分・試験から判断する。重大な破壊、未実行gate、対象HEAD不一致は停止。通常の改善提案はparkして期限/再検討条件を付ける。
5. 一人のintegratorが候補へ統合し、統合後HEADを検証する。レビュー後の変更は影響箇所を再確認する。workerのexit 0やレビュー文章だけで完了としない。
6. isolated installと実タスクで動かし、利用者が分かる改善を示す。人が行うのは価値判断と必要な最終承認で、diffの運搬・ログ収集は自動化する。
7. 結果から次の一つを選ぶ。計画を更新する際は前提がどう変わったかを一文で残す。

30分ごとの健康確認は、まず差分・試験・進捗・枠を機械で確認する。LLMの監査は統合前、高リスク変更、停滞検出時に限定する案。現行の定時監査を廃止する場合は、そのpolicyも同じ変更で更新する。データ喪失や整合性破壊は現在milestone外でも最優先へ再分類できる経路を設ける。

## 最初に着手する具体的なpacket案

| ID | 成果物 | 依存/担当候補 | 検証 |
|---|---|---|---|
| REC-01 | 現在状態をGit・環境・ledgerの実測へ合わせ、実行ボードの順序を変更 | Codex指揮。ユーザーの再計画依頼を根拠にする | project docs / AI docs、単一ボードの確認 |
| REC-02 | 現在HEADのRust基準点、toolchainと再実行コマンド | 契約内worker A。REC-01の棚卸しと並列可能 | fmt、clippy、test --workspace --locked、CLI smoke |
| REC-03 | 課金禁止の起動/停止とrouting不一致の解消 | 契約内worker B。REC-02とは別の基盤write set | 偽CLIによる課金・枠切れ・fallback検査、既存基盤テスト |
| REC-04 | first-seal経路の観測、説明不足・誤解・復旧の優先順位 | Fable/Grokの利用可能な枠。実行部分はREC-02待ち | isolated fixture、経路別結果、手順と意味の理解を分離して記録 |
| REC-05 | REC-04の最上位の摩擦を一つ修正して再試用 | 実装と別family review | 新しい回帰fixture、統合後gate、実利用のbefore/after |

最初の数稼働日はREC-01〜03を進め、その後REC-04〜05で最初の利用可能な改善を出す。環境・認証・残量次第で日程は変わる。モデルの総当たり評価や全ファイル再レビューを先行する必須条件にはしない。

基盤変更の最小範囲は、課金禁止・認証経路確認、routeの一元化、停止と再開、Grokのworktree/制限の実効性。巨大なagent platformは作らず、CodeFireの `crates/` へschedulerを入れない。JSONを正本と称するなら実装が読み込むか生成元にし、各言語へ独立した既定値を手書きしない。

runtime検査がClaudeのroleをCodex設定へ要求する箇所は、検査を緑にするためだけに転記しない。Codex内のsubagentと外部のClaude/Grok CLI実行を別のruntimeとして表現し、それぞれ実際に対応する設定を検査する。CLIバージョンadapterは現在の0.153系と、残存する0.146系の記載を照合する。

## 実測で配分を改善する

初期は既存CFB/CFRから、局所バグ・CLI契約/UX・永続化/復旧・性能の4種、合計6–8件程度の小さい評価集合を作る。既存eval/fixtureを再利用する。旧履歴に正解が見える課題は修正後情報を渡さず、ただし公開履歴への学習混入の可能性は明記する。

同じbase・要件・制限・検証条件でFableとGrokを比較する。native CLIが異なるため、モデル単体ではなく「モデル＋CLI」の運用比較と呼ぶ。課金禁止でFableを使えない契約なら、Fableのローカル評価は未測定とし、契約内候補だけで実施する。

品質は機械的な合否と欠陥の再現を優先する。LLMの採点は補助。初回pass、レビューで修正した回数、見逃した重大欠陥、統合後再発、経過時間、人の介入分数、各サービスの利用枠増分を記録する。合意した二つのモデルが同時に間違うこともあるので、重要不変条件には独立した反例試験を使う。

最初から全仕事を二重実装せず、高リスクまたは評価対象の少数だけ比較する。通常業務の結果も蓄積し、2cycleごとに配分を見直す。少数課題の結果から全領域の優劣を断定しない。

| 追跡する指標 | 用途 |
|---|---|
| 週あたり、実利用で効果を確認した採用変更数 | 開発の実効スループット |
| issue着手から利用確認までの中央値 / p90 | レビュー・統合・枠待ちの詰まりを見つける |
| 統合後回帰、再open、重大欠陥見逃し | 速度と品質の両立を確認 |
| first-seal時間、誤解、手動修正、別タスクでの再利用 | プロダクトの成長を確認 |
| provider別枠消費とquota待ち時間 | 翌週の配分を修正。非公開換算率を推測しない |
| 人の介入分数 / 採用変更 | 管理の複雑化でユーザーの負担を増やしていないか |

書類の完了条件だけを満たすcycleが続くなら、実装・実利用へ配分を戻す。利用者が価値を感じないなら、機能追加より対象課題と最小経路を変える。これを「計画→実装→合格」で止まらない継続的な製品改善の基準とする。

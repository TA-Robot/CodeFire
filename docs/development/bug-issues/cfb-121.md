# CFB-121: local commit publishes a newly stored commit without sealed validation

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | bug |
| Area | Commit / Branch publish integrity |
| Observed while | 2026-07-11 canonical source-document audit before new product development |

## Original Observation

Before this fix, Rust `run_commit` wrote the root objects, constructed and optionally signed the commit payload, stored the commit object, and then updated the branch head. It did not call `validate_sealed_commit` on the new commit between storage and publication. The store validated record identity during write, but the stronger root/certificate/parent contract was a separate consuming-boundary operation.

## Original Reproduction

The original counterexample required a test-only candidate-construction fault producing a
content-addressed commit with an inconsistent certificate, root, or parent. Those injections are now
retained by `CommitCandidateCorruptionKind` and prove rejection at the explicit pre-publication gate.

## Why It Matters

Branch-head publication is the candidate visibility point. A future construction bug or format change can publish a locally generated object that is hash-valid but not a valid sealed commit, leaving readers to discover the corruption after visibility changed.

## Historical Workaround

Before the fix, users could run `doctor` and a sealed `show`/branch validation after commit before treating the head as durable evidence. That could not make the publication itself atomic.

## Chosen Fix

Call the sealed-commit validator after storing the new commit and before changing branch/opened state. On failure, keep the old head, retain a diagnosable pending transaction marker, and return structured recovery guidance.

## Implemented Fix

`run_commit` now predeclares every immutable transaction object, stores the candidate commit, and
leaves the marker at `validating_candidate_commit` while it calls
`validate_sealed_commit_pinned_with_cache`. It reads the authenticated candidate through the returned
`ValidatedSealedCommit` and applies `verify_local_commit_signature` before storing the branch
snapshot or publishing any mutable branch/opened reference.

Seal or signature failure leaves the old branch head and opened-registry base unchanged and retains
the pending transaction with the stored candidate object for diagnosis. On success the branch
snapshot object is stored before its reference, and the validated object-store subject is rechecked
immediately before and after branch-reference publication. The command-scoped validation cache
avoids redundant traversal of the same sealed candidate graph.

## Acceptance Criteria

- Branch and opened-registry heads remain unchanged when the newly stored commit fails sealed validation.
- The pending transaction identifies the failed pre-publication phase and written immutable objects.
- Focused failpoint tests cover invalid certificate, wrong/missing root, invalid parent, and optional signature-policy boundaries.
- Successful commit does not validate the same reachable graph redundantly without an explicit command-scoped cache/evidence rationale.

## Evidence

- `crates/codefire-cli/src/main.rs::run_commit` places pinned sealed validation and local-signature
  authentication between candidate storage and branch-snapshot/reference publication.
- `crates/codefire-cli/src/signatures.rs::verify_local_commit_signature` verifies a locally signed
  candidate with the same trusted key used to construct it and enforces the required-signature
  policy.
- `crates/codefire-store/src/lib.rs::ValidatedSealedCommit::ensure_subject_identity` binds the
  validation result to the object-store subject across mutable reference publication.

## Regression Evidence

- `crates/codefire-cli/src/tests.rs::commit_candidate_validation_rejects_corruption_before_publishing_branch_state`
  covers invalid certificate, missing root, wrong root type, and invalid parent. Every case leaves a
  pending `validating_candidate_commit` marker with the candidate stored while branch and
  opened-registry heads remain unchanged.
- `crates/codefire-cli/src/tests/signature_boundary.rs::required_signed_candidate_with_tampered_digest_is_rejected_before_reference_publication`
  proves a present but tampered required signature is rejected before mutable reference publication,
  preserves the prior branch/registry values, and remains visible to doctor as a pending transaction.
- `crates/codefire-cli/src/tests.rs::required_commit_signature_without_key_is_prepublication_and_diagnosable`
  proves the required-signature/no-key boundary publishes no candidate object or reference and leaves
  a diagnosable transaction at `started`.

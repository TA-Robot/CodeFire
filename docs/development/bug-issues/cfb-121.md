# CFB-121: local commit publishes a newly stored commit without sealed validation

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | bug |
| Area | Commit / Branch publish integrity |
| Observed while | 2026-07-11 canonical source-document audit before new product development |

## Observation

Rust `run_commit` writes the root objects, constructs and optionally signs the commit payload, stores the commit object, and then updates the branch head. It does not call `validate_sealed_commit` on the new commit between storage and publication. The store validates record identity during write, but the stronger root/certificate/parent contract is a separate consuming-boundary operation.

## Reproduction

Add a test-only fault/counterexample at commit construction that produces a content-addressed commit with an inconsistent certificate or wrong root type, then assert that branch publication is attempted without an explicit sealed validation gate.

## Why It Matters

Branch-head publication is the candidate visibility point. A future construction bug or format change can publish a locally generated object that is hash-valid but not a valid sealed commit, leaving readers to discover the corruption after visibility changed.

## Workaround

Run `doctor` and a sealed `show`/branch validation after commit before treating the head as durable evidence. This cannot make the publication itself atomic.

## Candidate Fix

Call the sealed-commit validator after storing the new commit and before changing branch/opened state. On failure, keep the old head, retain a diagnosable pending transaction marker, and return structured recovery guidance.

## Acceptance Criteria

- Branch and opened-registry heads remain unchanged when the newly stored commit fails sealed validation.
- The pending transaction identifies the failed pre-publication phase and written immutable objects.
- Focused failpoint tests cover invalid certificate, wrong/missing root, invalid parent, and optional signature-policy boundaries.
- Successful commit does not validate the same reachable graph redundantly without an explicit command-scoped cache/evidence rationale.

## Evidence

- `crates/codefire-store/src/lib.rs::store_object`
- `crates/codefire-store/src/lib.rs::validate_sealed_commit`

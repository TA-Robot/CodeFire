# CFB-055: `scan --json` changed atom shape is easy to misread

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | medium |
| Type | automation-json |
| Area | scan JSON schema |
| Observed while | extracting changed Atom samples during `ExperimentIterationPlanner` dogfooding |

## Observation

`scan --json` returns `data.changed_atoms` as an array of Atom ID strings. A reasonable consumer may expect objects with fields such as `id`, `kind`, `path`, or `hash`, especially because `open_fires` is an array of detailed objects.

## Reproduction

```bash
codefire scan --path . --json --metrics \
  | jq '[.data.changed_atoms[0:5][]?.id]'
```

This fails because each entry is a string, not an object.

## Why It Matters

Automation code must branch on command-specific payload details that are not obvious from the field name. The shape also makes it harder to move from a changed Atom ID to the related detail without knowing to call another command.

## Workaround

Treat `changed_atoms` as string IDs and call `context --atom <id> --json` or `explain atom <id> --json` for detail.

## Candidate Fix

Rename the current field to `changed_atom_ids`, add a bounded `changed_atoms_sample` object array, or document the schema explicitly in `automation_interface.md` with examples.

## Acceptance Criteria

- The scan JSON schema makes string-vs-object shape unambiguous.
- Automation docs include a sample `jq` for changed Atom IDs and detail retrieval.
- Backward compatibility is preserved or a schema version bump is documented.

## Evidence

- During iteration planner work, `jq` failed with `Cannot index string with string "id"` against `data.changed_atoms`.

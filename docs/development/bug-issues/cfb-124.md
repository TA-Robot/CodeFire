# CFB-124: live scan and verify mutate shared state without the repository lock

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | bug |
| Area | Scan / Verify / Repository state concurrency |
| Observed while | 2026-07-11 canonical source and lock-boundary audit |

## Observation

The production `scan` and `verify` command handlers call `compute_scan(..., true)` or `compute_verify(..., true)` without first acquiring `RepoLock`. Those paths write `fires.json`, `scan.json`, `verification.json`, opened-registry state, active state, and branch state. Callers such as commit, batch extinguish, and lifecycle operations do acquire the repository lock, so a direct live scan or verify can interleave with a locked mutation while bypassing the same serialization boundary.

## Reproduction

Run direct `scan` or `verify` concurrently with another state-changing command against the same open directory. Add a failpoint between individual state-file writes to make an interleaving deterministic, then compare fires, scan, verification, opened registry, active state, and branch state.

## Why It Matters

The live scan result is an input to Fire, resolution, verification, and commit decisions. Interleaved individually atomic writes can lose a newer update or leave mutually inconsistent state files even though the other command correctly held `RepoLock`. This weakens the advertised concurrency boundary and makes failures timing-dependent.

## Workaround

Serialize all live `scan`, `verify`, extinguish, batch, and commit invocations for one repository. Do not run them concurrently until the shared lock boundary is fixed and tested.

## Candidate Fix

Put one lock-owning boundary around every live scan/verify mutation, while retaining an explicitly read-only compute path for status, explain, dry-run, and nested callers that already own the lock. Make lock ownership visible in function names or types so nested acquisition and accidental unlocked persistence both fail review.

## Acceptance Criteria

- Direct live scan and verify acquire the same repository lock used by other mutable open-state commands.
- Nested callers have one explicit lock owner and cannot deadlock by reacquiring it.
- Read-only preview/explain paths do not mutate or acquire a write lock unnecessarily.
- Deterministic concurrency/failpoint tests cover scan-versus-verify and scan/verify-versus-extinguish or commit.
- Every successful write sequence leaves fires, scan, verification, opened registry, active state, and branch state mutually consistent, or leaves a diagnosable recovery marker.
- Lock timeout/failure remains machine-readable through the production JSON envelope.

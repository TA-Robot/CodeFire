# CFB-024: Local workflow subcommands reject help flags

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | CLI help |
| Observed while | checking scan/verify path syntax after v0.7 install |

## Observation

`codefire scan --help` and `codefire verify --help` returned unsupported option errors instead of showing command-specific usage.

## Reproduction

```bash
codefire scan --help
codefire verify --help
```

## Why It Matters

When an AI agent tries a wrong option, the next best recovery path is usually `--help`. If help itself fails, the agent tends to retry variants blindly or inspect source files.

## Workaround

Before v0.8, read top-level `codefire help` or the project documentation.

## Fix

v0.8 adds early help detection for local workflow commands and a `subcommand_help` table for the dogfooding-critical commands: `status`, `scan`, `verify`, `fire`, `extinguish`, `commit`, `branch`, `storage`, `doctor`, `evidence`, `show`, and `diff`.

## Acceptance Criteria

- `codefire scan --help` prints scan usage.
- `codefire verify --help` prints verify usage.
- Help text documents path, JSON, and metrics flags where applicable.
- Existing command behavior without help flags is unchanged.

## Evidence

- Regression coverage: help routing is exercised by CLI command registration/docs tests and command parser tests.
- Verification: `cargo test -p codefire-cli --bin codefire-rs -- --nocapture`.

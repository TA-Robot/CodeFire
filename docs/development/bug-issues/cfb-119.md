# CFB-119: open ignores branch record state when opened registry is missing

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | bug |
| Area | Branch open / State recovery |
| Observed while | CodeFire open implementation review after branch-per-feature dogfood |

## Observation

`open_branch_from` loads the branch record, validates the sealed `head`, and then only checks whether the opened registry file exists:

```rust
let mut branch = load_branch_record(&repo_root, &options.branch)?;
let branch_head = required_string(&branch, &["head"])?;
codefire_store::validate_sealed_commit(&objects, &branch_head)?;
...
let registry_path = opened_registry_path(&repo_root, &options.branch);
if registry_path.exists() {
    return Err(CliError::Usage(format!(
        "branch is already open: {}",
        options.branch
    )));
}
```

It does not inspect `branch["state"]` before planning or applying open. If the opened registry is missing or corrupted while the branch record still says `open-consistent` or `open-burning`, `open` can materialize the sealed branch head into a new directory and overwrite the branch state to `open-clean`.

## Reproduction

Code path review:

```bash
nl -ba crates/codefire-cli/src/main.rs | sed -n '5220,5335p'
```

State-corruption scenario:

1. A branch is open and has unsealed work.
2. `.codefire/opened/<branch>.json` is removed or becomes unreadable, but the branch record still has an open state.
3. `codefire open <branch> <new-path>` sees no opened registry and proceeds from the sealed `head`.

## Why It Matters

The branch record state and opened registry together represent the lifecycle of an open branch. Treating the registry as the only guard makes recovery brittle: the user can accidentally create a second open directory from an old sealed head while the branch metadata still indicates open work. In branch-per-feature workflows this can hide or strand active changes.

## Workaround

Before reopening a branch after any registry or filesystem problem, manually compare:

- `.codefire/branches/<branch>.json`
- `.codefire/opened/<branch>.json`
- the expected open directory marker `.codefire-open`

If the branch record is `open-consistent` or `open-burning`, recover the existing open directory or explicitly discard it before opening again.

## Candidate Fix

Make `open` validate branch lifecycle state before checking only the registry path. A conservative rule is:

- allow `closed` branches to open;
- allow `open-clean` only when the registry and marker are consistent with the requested recovery mode;
- reject `open-consistent` and `open-burning` with a structured recovery error if the opened registry is missing.

## Acceptance Criteria

- `codefire open` rejects a branch record in `open-consistent` or `open-burning` even when the opened registry file is missing.
- The error includes repo, branch, branch state, expected registry path, and recovery next actions.
- A tested recovery command or documented manual procedure exists for registry-loss cases.
- Normal closed-branch open behavior is unchanged.

## Evidence

- `crates/codefire-cli/src/main.rs::open_branch_from` reads `branch["head"]` but does not check `branch["state"]`.
- The only already-open guard is `opened_registry_path(...).exists()`.

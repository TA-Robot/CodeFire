# CFB-131: remote copy rewrites legacy short object identity

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | compatibility |
| Area | Remote object graph copy / legacy object identity |
| Observed while | running the fresh installed-binary mutable Dogfood sandbox |

## Observation

The Store accepts authenticated historical object records whose public ID uses the legacy 12-hex
digest prefix. File-remote upload reads those records successfully, but `copy_object_record`
recreates each destination object through `store_object(type, payload)`. That writer always derives
the current 24-hex public ID. The remote layer then compares the returned current ID to the source
legacy ID and aborts:

```text
invalid CodeFire repository: copied object identity changed:
expected CF-COMMIT-f825fc13207f, stored CF-COMMIT-f825fc13207f6055b36c7f49
```

`write_object_records`, used by received remote bundles, has the same normalization pattern and can
reject otherwise valid legacy records for the same reason.

## Reproduction

1. Copy the configured Algorithm `.codefire` repository into an independent temporary sandbox.
2. Run `migrate apply` there to fill the two registered layout gaps; exact replay succeeds as a
   no-op.
3. Run the fresh installed binary:

```bash
codefire upload main cf:///tmp/codefire-stage1-dogfood/remote/org/app/main --json
```

Upload exits 20 with one JSON envelope and `invalid_repository` diagnostic at the first reachable
legacy short-ID commit.

## Why It Matters

CFB-128 restores local readability and a non-destructive current-profile bridge, but a repository
cannot use remote backup/clone as that bridge if transport silently changes authenticated public
object identity. Rewriting IDs would also require rewriting every parent/root/reference edge and
would no longer be a byte-preserving transfer of the sealed graph.

## Workaround

Do not upload the affected legacy history. A local sandbox can be constructed by copying internal
records, but that bypasses the supported remote workflow and is not acceptable for Dogfood close.

## Candidate Fix

Add one Store-owned exact-record publication primitive:

- validate the supplied record's type, full digest, payload, and either supported public-ID width;
- publish under that exact validated ID through the existing no-follow/capability/link-race path;
- require exact identity and canonical payload agreement when the destination already exists;
- use it for file-remote graph copy and received-record writes;
- keep ordinary new-object construction on the current 24-hex writer.

## Resolution

- Added `codefire_store::store_object_record` for transfer/migration boundaries. It revalidates the
  supplied complete record and publishes its exact supported 12- or 24-hex ID through the existing
  bounded, no-follow, create-new temp, no-replace hard-link, collision, and subject-identity path.
- Kept `store_object` as the only new-payload constructor; it still always emits current 24-hex IDs.
- Routed file-remote graph copy and received bundle records through exact-record publication.
- Added Store regressions for legacy identity preservation/replay, invalid identity before write,
  and short-ID collision. Added a CLI regression covering legacy short-ID commit upload, repeated
  upload reuse, remote clone, sealed validation, and received-record replay.

## Acceptance Criteria

- A valid legacy 12-hex object graph uploads and clones without changing any object ID or edge.
- Current 24-hex graph transfer remains unchanged.
- Invalid hash/ID/type, short-ID collision, existing-record mismatch, symlink, and publication race
  still fail closed.
- Repeated transfer reuses the exact destination record without rewriting it.
- The installed-binary sandbox can remote-upload the legacy Algorithm head, clone/open it, and
  create a strict current-profile bridge commit through the normal workflow.

# CFB-094: status next_actions omit commit for non-Atom-only pending changes

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | Status / Next actions |
| Observed while | `algorithm-evolution-agent-lab` cycle 6 dogfooding for `ResearchCyclePlanLint` |

## Observation

After adding `ResearchCyclePlanLint`, the algorithm project was sealed with `CF-COMMIT-e9809fabb758032363e80407`. A follow-up edit then updated only `docs/development/history.md` inside the algorithm project to record that CodeFire commit ID.

`codefire status --path subprojects/algorithm-evolution-agent-lab --json` returned:

- `state:"open-clean"`
- `open_fires:0`
- `scan_prediction.changed_count:1`
- `scan_prediction.non_atom_changed_file_count:1`
- `scan_prediction.open_fire_count:0`
- `next_actions:[]`

The branch had pending non-Atom changes and no fires, so the next safe action should have been `codefire commit -m <message>`.

## Reproduction

```bash
codefire commit -m "Add research cycle plan lint" --path subprojects/algorithm-evolution-agent-lab --json
# edit only a non-Atom tracked file under the open directory
codefire status --path subprojects/algorithm-evolution-agent-lab --json
```

## Why It Matters

AI or scripted automation follows `next_actions`. If non-Atom-only changes produce no action, the automation can incorrectly treat the branch as clean even though `scan_prediction` already proves there are pending changes to seal.

This is separate from CFB-093: CFB-093 covered `open-burning` with changed atoms and zero fires. This issue covers `open-clean` persisted state with prediction-only non-Atom changes.

## Workaround

Run `codefire scan --json --path ...` and then manually run `codefire commit -m ... --path ...` when `changed_count > 0` and `open_fire_count == 0`.

## Candidate Fix

Make `status_next_actions_with_prediction` trust the recomputed scan prediction for commit readiness:

- if predicted `changed_count > 0`
- and predicted `open_fire_count == 0`
- and stored `status.open_fires == 0`

then return a commit next action, regardless of whether the persisted state label is `open-clean` or `open-burning`.

## Acceptance Criteria

- `status --json` recommends `commit` for non-Atom-only pending changes with zero open fires.
- clean status with no predicted changes still returns no next actions.
- status with open fires does not recommend commit.
- A unit test covers the non-Atom-only prediction case.

## Evidence

- Regression test: `automation::tests::clean_status_with_non_atom_prediction_suggests_commit`.
- Targeted test run: `cargo test -p codefire-cli automation::tests:: -- --nocapture`.
- Dogfood context: `algorithm-evolution-agent-lab` cycle 6 after `CF-COMMIT-e9809fabb758032363e80407`.

## Fix

Implemented in cycle 6 burn-down.

- Removed the `status.state == "open-burning"` requirement from prediction-driven commit action generation.
- `status_next_actions_with_prediction` now uses predicted pending changes and predicted zero open fires, while still checking stored `status.open_fires == 0`.

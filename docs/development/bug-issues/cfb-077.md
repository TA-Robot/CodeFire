# CFB-077: manual fire identity format differs from scan fire identity

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | Fire Identity |
| Observed while | probing manual fire dry-run/apply during cycle 2 dogfooding |

## Observation

Manual `fire --dry-run` and apply return `display_id: FIRE-001` and `fire_uid: fire_<12hex>`. Scan-generated fires now use digest-derived display IDs such as `FIRE-5EB996E6F4EC` and `fire_sha256_...` UIDs.

## Reproduction

```bash
cd subprojects/algorithm-evolution-agent-lab
codefire fire REQ-AUTO-033 --to DES-AUTO-015 --reason "dry run probe" --path . --dry-run --json
```

## Why It Matters

Mixed identity formats make logs and batch files harder to reason about. The previous scan fire ID reuse issue was fixed, but manual fires still look sequence-based and less stable.

## Workaround

Record both `display_id` and `fire_uid` for manual fires.

## Candidate Fix

Use the same stable digest-derived display ID and UID scheme for manual fires and scan fires.

## Acceptance Criteria

- manual fire display IDs are stable and non-sequential.
- manual fire UIDs use the same prefix/format family as scan fire UIDs.
- existing manual fire references remain readable.

## Evidence

- Observed during cycle 2 clean-state manual fire probe.
- Fixed by deriving manual fire `display_id` and `fire_uid` from the semantic fire key digest, matching scan fire's `FIRE-<12hex>` and `fire_sha256_<32hex>` family.
- Regression: `manual_fire_and_batch_validate_before_writing_fires`; dogfood `codefire fire CODE-AblationGenerator --to CODE-AntiOverfittingMonitor --reason "manual fire identity dry-run probe" --path . --dry-run --json`.

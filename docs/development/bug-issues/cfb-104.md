# CFB-104: merge apply marks target open-burning before persisting merge fires

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | bug |
| Area | Merge / Fire persistence |
| Observed while | branch workflow source review after branch-per-feature dogfood |

## Observation

The CLI spec says local merge execution generates merge fires and marks the target `open-burning`. The implementation writes merged files, records `pending_merge_parent` / conflict metadata, and sets the target open state to `open-burning`, but it does not persist `fires.json` during merge apply.

The actual `merge_changed` fires are generated later by `scan` or `verify`, because `compute_scan` switches fire reason to `merge_changed` when it sees `pending_merge_parent`.

## Reproduction

```bash
cd /workspace/project/subprojects/algorithm-evolution-agent-lab
codefire merge <source-branch> --into main
codefire status --path . 
```

Immediately after merge apply, text status can report `State: open-burning` with `Open fires: 0` until a scan or verify persists the generated merge fires.

## Why It Matters

Branch merge is a high-risk workflow step. If merge apply and fire persistence are split across commands, automation can observe an intermediate state that looks burning but has no listed fires. That weakens the intended "merge creates review work" contract and makes the next correct command depend on preview scan behavior rather than durable active state.

## Workaround

Fixed in branch workflow burn-down. Older binaries require running `codefire scan --path <target-open-dir> --json` or `codefire verify --path <target-open-dir> --json` immediately after merge before interpreting open fire counts.

## Candidate Fix

During merge apply, either persist merge-generated fires as part of the same operation or make the spec/output explicit that merge only records pending merge metadata and requires a follow-up scan. If persistence is added, keep it transactionally ordered with file writes and open state updates.

## Acceptance Criteria

- After merge apply, active `fires.json` contains merge-generated fires when merged changes affect linked atoms.
- Text `status` immediately after merge does not show `open-burning` with `Open fires: 0` for merge changes that will produce fires.
- Merge tests assert fire persistence before an explicit scan, or the spec and next_actions clearly require a scan-first workflow.

## Evidence

- Source review on 2026-06-12 found `apply_merge_result` sets pending merge metadata and open state, while `compute_scan` later turns pending merge state into `merge_changed` fires.
- Fixed by running persistent scan during merge apply after writing pending merge metadata, then preserving target `open-burning` state.
- Regression: `crates/codefire-cli/src/tests.rs::merge_branch_persists_merge_fires_during_apply`.

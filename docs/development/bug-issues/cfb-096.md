# CFB-096: status next_actions drop explicit path context

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | medium |
| Type | automation-json |
| Area | Status / Next actions path |
| Observed while | cycle 60 dogfood in `algorithm-evolution-agent-lab` |

## Observation

`codefire status --json --path subprojects/algorithm-evolution-agent-lab` correctly reports the target repo and predicts open fires for that open directory, but the returned `next_actions` omit the explicit path:

```json
[
  {"command": "codefire scan --json", "kind": "scan"},
  {"command": "codefire verify --details --json", "kind": "verify"},
  {"command": "codefire context --changed --json", "kind": "context_changed"}
]
```

The same command was run from `/workspace/project`, not from the algorithm open directory. Running those next actions verbatim from the same cwd would target the wrong repository/open directory or fail to recover the intended context.

## Reproduction

```bash
cd /workspace/project
codefire status --json --path subprojects/algorithm-evolution-agent-lab
```

## Why It Matters

AI agents and scripts commonly execute `next_actions[*].command` from the current process cwd. If `status --path <open-dir>` drops the path in its suggested commands, automation can scan, verify, or inspect the wrong CodeFire repository. This is the same class of automation risk fixed earlier for scan and verify next actions, but the status path-preservation surface still misses it.

## Workaround

Manually append the original path to each suggested command:

```bash
codefire scan --json --path subprojects/algorithm-evolution-agent-lab
codefire verify --details --json --path subprojects/algorithm-evolution-agent-lab
codefire context --changed --json --path subprojects/algorithm-evolution-agent-lab
```

## Candidate Fix

Thread the original status action path into `status_next_actions_with_prediction` and render it in both the human command string and machine-readable `target` / `context` fields. Preserve concise commands only when status was invoked without an explicit path.

## Acceptance Criteria

- `status --json --path <open-dir>` next actions retain `--path <open-dir>`.
- `status --json --path=<open-dir>` behaves the same.
- JSON `target` or `context` includes the original path/open directory.
- Regression coverage asserts path preservation for scan, verify, and context next actions emitted by status.

## Evidence

- Observed on 2026-06-12 during cycle 60 dogfood after adding `FinalManifestGate`.
- `status` output had `repo: "/workspace/project/subprojects"` and `scan_prediction.open_fire_count: 10`, but next action commands were pathless.

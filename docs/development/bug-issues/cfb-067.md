# CFB-067: commit success JSON has null top-level repo and plan-like next action

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | Commit / JSON Contract |
| Observed while | committing `ExperimentEvidencePackBuilder` in the algorithm dogfood project |

## Observation

`codefire commit --path . -m "Add experiment evidence pack builder" --json` succeeded, but the top-level envelope had `"repo": null`. The successful result also used `data.type = "codefire_plan_result"` and retained `data.plan.next_actions` containing `kind: apply_commit`, even though the commit had already been applied.

## Reproduction

```bash
cd subprojects/algorithm-evolution-agent-lab
codefire commit --path . -m "Add experiment evidence pack builder" --json
```

Observed fields:

```json
{
  "command": "commit",
  "ok": true,
  "repo": null,
  "data": {
    "type": "codefire_plan_result",
    "plan": {
      "would_apply": true,
      "next_actions": [{"kind": "apply_commit"}]
    }
  }
}
```

## Why It Matters

Automation should be able to treat top-level envelope fields consistently. A successful mutating command with `repo: null` forces command-specific parsing. Keeping an apply next action after the operation has already applied can make an AI tool think the command only planned the mutation.

## Workaround

Read `data.plan.open_dir`, `data.plan.branch`, and the emitted commit object indirectly. Do not trust `data.plan.next_actions` after a successful apply.

## Candidate Fix

Split commit dry-run plan and commit apply result into separate typed data models. For apply success, populate top-level `repo`, include `commit_id`, `branch`, `parents`, `changed_atom_count`, `resolved_fire_count`, and omit apply next_actions.

## Acceptance Criteria

- commit success JSON has a non-null top-level `repo`.
- commit apply result uses a `codefire_commit_result` data type, not `codefire_plan_result`.
- apply-only next_actions are absent after successful apply.
- dry-run still returns an operation plan.

## Evidence

- Observed during cycle 2 dogfooding after all algorithm tests passed and open fires were extinguished.
- Fixed by returning typed `codefire_commit_result` data with top-level `repo` from execution context.
- Applied commit results do not expose apply-only next actions; dry-run plans still expose path-qualified apply commands.
- Regression: `commit_dry_run_json_reports_blockers_and_bounds_changed_atoms`; dogfood `codefire commit --path . -m "dry-run probe" --dry-run --json`.

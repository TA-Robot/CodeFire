# CFB-126: import idempotency replay is not bound to the requested payload

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | bug |
| Area | Import / Idempotency conflict detection |
| Observed while | 2026-07-11 canonical idempotency-invariant audit |

## Observation

`import_existing_project` looks up an import marker by target path and idempotency key before validating the current request. The marker stores the earlier result fields but no canonical request payload or payload hash. `load_import_idempotency_marker` therefore returns that prior result without comparing the requested branch or other semantic options. Reusing one key for a different import request can be reported as a successful replay rather than an idempotency conflict.

## Reproduction

Import a target with an idempotency key, then retry the same target and key while requesting a different branch or another semantic option. Compare the returned replay with the second request. A focused unit test can construct the saved marker directly so it does not depend on mutating an already imported directory through external setup.

## Why It Matters

An idempotency key is safe only when it identifies one operation payload. Returning an earlier success for a different request can make automation believe the requested branch or policy was applied when the stored result describes another operation. It also makes `import` weaker than the common idempotency contract used by other mutating commands.

## Workaround

Use a globally unique key for every semantically distinct import request and manually verify the replayed `branch`, target, and result fields. Do not rely on import replay to reject key reuse with different options.

## Candidate Fix

Define a canonical import idempotency payload before lookup, store its operation/scope/payload hash through the shared helper, and require exact verification before replay. Version or migrate existing result-only markers explicitly instead of silently treating them as payload-bound.

## Acceptance Criteria

- Exact import retries return the original result without repeating writes.
- Reusing a key with a different branch, target scope, or other semantic option returns the standard typed idempotency conflict.
- Import records bind operation, scope, key, canonical payload hash, and replay result using the shared invariant.
- Legacy result-only markers have an explicit readable/reject/migration policy.
- Tests cover exact replay, branch mismatch, target/scope mismatch, malformed marker, and concurrent retry behavior.

## Fixed In

- `import_existing_project` now normalizes the target and builds `import_idempotency_payload` before marker lookup. The canonical payload binds the operation, normalized target scope, target, branch, payload version, and semantic import mode.
- Version 2 import idempotency records store the operation, scope, key, payload version, and shared canonical `payload_hash` in `hash_only` mode together with the replay result. `verify_import_idempotency_marker` checks those fields and delegates exact hash/key verification to the shared `verify_idempotency_record` invariant before returning a replay.
- The durable import transaction independently records scope, payload version, payload hash, target, and branch. `ImportTransaction::verify_request` rejects a conflicting resume, while the bootstrap/repository locks serialize exact concurrent retries and validate that the replayed result still belongs to the bound target.
- Legacy version 1 result-only markers are explicitly readable only far enough to classify them, then fail closed with typed `IdempotencyConflict` because they cannot prove payload identity. Malformed v2 records and results for another target are reported as invalid repository state instead of successful replay.

Regression evidence in `crates/codefire-cli/src/import_workflow.rs`:

- `import_idempotency_exact_replay_is_payload_bound_and_hash_only` checks exact replay and every persisted v2 binding field without storing the plaintext payload.
- `import_idempotency_rejects_branch_mismatch`, `import_idempotency_rejects_scope_mismatch`, and `import_idempotency_rejects_semantic_options_mismatch` cover all current semantic request dimensions.
- `import_idempotency_rejects_malformed_marker`, `import_idempotency_rejects_result_for_a_different_target`, and `import_idempotency_rejects_legacy_result_only_marker` cover malformed, wrong-subject, and legacy fail-closed behavior.
- `concurrent_exact_import_with_wait_replays_the_winner` proves two serialized exact requests converge on one base commit and exactly one caller receives the replay result.

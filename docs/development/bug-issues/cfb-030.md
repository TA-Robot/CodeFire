# CFB-030: Metrics report unmeasured phases as 0ms

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | low |
| Type | performance |
| Area | `--metrics` |
| Observed while | comparing scan and verify metrics during runbook work |

## Observation

Metrics include phases with `elapsed_ms: 0` and `measured: false`.

## Reproduction

```bash
codefire scan . --metrics --json
codefire verify . --metrics --json
```

## Why It Matters

Performance tooling may aggregate unmeasured phases as real zero-cost phases.

## Workaround

Check `phases[].measured` before using timing values.

## Candidate Fix

Represent unmeasured phase elapsed time as `null`, or omit it from aggregate timing summaries.

## Fix

v0.8 emits `null` for unmeasured phase timing values in the JSON timing map while preserving measured phase timings.

## Acceptance Criteria

- Unmeasured phases cannot be mistaken for measured 0ms work.
- Existing measured phase timings remain stable.

## Evidence

- `scan` metrics showed atom extraction, trace parse, and fire build as `0ms` with `measured=false`.
- Regression coverage: `metrics_attach_to_status_scan_and_verify_data`.
- Verification: `cargo test -p codefire-cli --bin codefire-rs -- --nocapture`.

# CFB-075: bounded scan next_actions do not explain how to recover omitted actions

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | medium |
| Type | automation-contract |
| Area | Automation JSON / Bounded Next Actions |
| Observed while | scanning `ClaimReleaseGate` changes |

## Observation

When `scan --json` produced 6 open fires, next_actions hit the bound and ended with `kind: next_actions_omitted`. The marker reported only an omitted count and suggested `codefire status --json`, but status does not return the omitted fire-specific context/extinguish actions.

## Reproduction

```bash
cd subprojects/algorithm-evolution-agent-lab
codefire scan --path . --json --metrics
```

Observed marker:

```json
{
  "command": "codefire status --json",
  "kind": "next_actions_omitted",
  "reason": "additional next actions were omitted to keep the command result bounded",
  "target": {
    "limit": 12,
    "omitted": 3
  }
}
```

## Why It Matters

Bounded next_actions are good, but automation needs a reliable way to recover omitted actions or understand their type. A status command is not equivalent to rerunning scan with a larger action budget.

## Workaround

Read `data.open_fires` from scan and reconstruct context/extinguish actions manually.

## Candidate Fix

Add omitted action metadata such as `omitted_by_kind`, `first_omitted_targets`, and a recovery command that actually returns the omitted action class, for example a higher-limit scan/context command.

## Acceptance Criteria

- `next_actions_omitted` reports omitted action counts by kind.
- The recovery command can retrieve the omitted action class.
- Tests cover scan with more open fires than the next_action cap.

## Evidence

- Observed during cycle 2 dogfooding with `ClaimReleaseGate`, where 6 open fires caused 3 actions to be omitted.

# CFB-109: branch lock contention lacks retry-oriented recovery actions

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | low |
| Type | UX bug |
| Area | Branch / Lock recovery |
| Observed while | parallel branch dry-run probing during algorithm dogfood |

## Observation

Running multiple CodeFire branch workflow dry-runs in parallel can produce lock contention errors. The JSON envelope includes the lock path, owner pid, and timestamp, but `repo` is `null` and `next_actions` is empty.

## Reproduction

Run several branch commands against the same algorithm repo at the same time, for example:

```bash
codefire open main /workspace/project/subprojects/algorithm-evolution-agent-lab-main-second --dry-run --json
codefire close feature/name-ci-note-md --dry-run --json
codefire merge main --into main --dry-run --json
```

When one command holds the repo lock, the others can fail with:

```text
kind: lock_contention
repo: null
next_actions: []
```

## Why It Matters

AI agents often parallelize independent probes. If CodeFire commands serialize on a repo lock, the failure should be easy to classify as retryable and should tell the agent which repo to retry against after waiting.

## Workaround

Run CodeFire branch commands sequentially for the same repo. Retry after the lock holder exits.

## Candidate Fix

Improve lock contention envelopes with the repo path, retry guidance, and a bounded wait/retry next action. Consider whether read-only dry-run commands can avoid the exclusive lock when safe.

## Acceptance Criteria

- Lock contention JSON includes non-null repo when the repo root is known.
- Diagnostics include whether the operation is safe to retry.
- Next actions include a wait/retry suggestion or a lock inspection command.
- Tests cover lock contention envelope shape.

## Evidence

- 2026-06-12 branch probe produced lock contention for parallel `open`, `close`, and `merge` dry-run commands against `/workspace/project/subprojects/.codefire/locks/repo.lock`.

## Fixed In

- CFB-105..CFB-119 burn-down: implemented branch lifecycle guards, merge freshness checks, remote clone dry-run/state safety, Markdown process-ID filtering, and non-Atom change visibility.

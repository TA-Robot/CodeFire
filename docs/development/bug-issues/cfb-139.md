# CFB-139: Prepared-stage recovery deletes a replacement file after preflight

## Summary

| Field | Value |
|---|---|
| Status | investigating |
| Milestone | MS-recovery-baseline |
| Severity | high |
| Type | correctness / recovery / ownership |
| Area | Store prepared object stage recovery |
| Observed while | REC-06 full source gate after CLI782 + integration7 + Core89 passed |

## Observation

`prepared_object_stage_recovery_preserves_name_replacement_before_unlink` replaces a candidate in its
before_unlink hook. Recovery deletes the replacement, causing ENOENT at the preservation assertion. A
subsequent debug Drop assertion aborts the test process during unwind. This reproduces alone; the destructor
panic is not a reason to weaken the ownership invariant or remove the preservation assertion.

## Reproduction

```bash
source docs/development/tools/rust_env.sh
cargo test --locked -p codefire-store tests::prepared_object_stage_recovery_preserves_name_replacement_before_unlink -- --exact --nocapture
```

Do not count a zero-test filter result as a passing reproduction.

## Why It Matters

Recovery must not remove unrelated data replacing a previously inspected staging file. Device/inode
values can be reused after unlink, so a stored number is not proof of uninterrupted object identity.

## Diagnosis

`recover_prepared_object_stages` retains (ObjectStoreIdentity, frame_bytes) per candidate. Inspection's
read handle is closed before the hook; final unlink checks only file/link metadata and identity. On Unix
identity is dev+ino. Inode reuse was independently observed in 10/10 separate delete/recreate cycles under
the same TMPDIR; inode values were not instrumented inside the failing Rust test itself.

## Candidate Fix

Bind recovery to the inspected file object through the final destructive boundary, with bounded ownership
and accounting. Consider pinned handles and content revalidation as appropriate; dev+ino or timestamps
alone are not immutable identity. Preserve existing non-following, unknown/future/mismatched-candidate,
ledger cancellation and resource-limit behavior. Do not claim protection against all hostile filesystem
races without an actual supported exclusion mechanism.

## Acceptance Criteria

- Existing replacement-before-unlink test passes repeatedly and recovery preserves the replacement bytes.
- Regression makes the identity lifetime hazard deterministic rather than relying on chance inode reuse.
- In-place tampering cannot be mistaken for unchanged owned content within the supported recovery boundary.
- True stale owned candidates can still be recovered; unknown/foreign/linked candidates are preserved.
- Handle/memory/read work is bounded and released on cancellation/error; no weakened destructor ownership assertion.
- Focused Store tests, strict Clippy, and final full workspace gate pass.

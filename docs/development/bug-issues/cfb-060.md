# CFB-060: Context and explain unknown Atom errors ignore `--json`

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | automation-json |
| Area | context / explain |
| Observed while | probing Atom detail retrieval before `ExperimentRiskRegister` implementation |

## Observation

Unknown Atom selectors return plain text errors even when `--json` is requested.

## Reproduction

```bash
codefire context --atom DOES-NOT-EXIST --json
codefire explain atom DOES-NOT-EXIST --path . --json
```

## Why It Matters

Agents need to distinguish an unknown Atom from command failure or malformed JSON. The current behavior forces text parsing.

## Workaround

Fixed. JSON callers can inspect `diagnostics[0].kind == "unknown_target"` and follow the `refresh_scan` next action.

## Candidate Fix

Implemented in the global burn-down pass.

## Fix

- `context --json` now catches parse and target resolution failures and emits `codefire.command_result.v1` instead of plain text.
- `explain --json` now uses the same JSON failure envelope for unknown Atom/fire targets.
- `CliError::Usage("unknown atom: ...")` and `CliError::Usage("unknown fire: ...")` map to diagnostic kind `unknown_target`.
- The JSON failure includes a `refresh_scan` next action so automation can refresh Atom/fire state before retrying.

## Acceptance Criteria

- Unknown selector errors produce JSON when `--json` is present.
- `diagnostics[0].kind` identifies the selector failure as `unknown_target`.
- Text mode behavior remains human-readable.

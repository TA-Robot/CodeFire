# CFB-074: explain next_actions use a different schema from other command envelopes

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | medium |
| Type | automation-contract |
| Area | Automation JSON / Next Action Schema |
| Observed while | explaining a fire during `ClaimAuditTrailBuilder` dogfooding |

## Observation

`codefire explain fire ... --json` returns next actions with fields `id`, `description`, and `context`. Other command envelopes such as scan, status, verify, and context generally use `kind`, `reason`, and `target`.

## Reproduction

```bash
cd subprojects/algorithm-evolution-agent-lab
codefire explain fire FIRE-9856EB644D66 --path . --json
```

Observed:

```json
{
  "next_actions": [
    {
      "id": "context_fire",
      "description": "inspect source, target, and trace context for this fire",
      "context": {"display_id": "FIRE-9856EB644D66"},
      "command": "codefire context --fire FIRE-9856EB644D66 --json"
    }
  ]
}
```

## Why It Matters

An AI/tool executor should be able to read next actions uniformly across commands. Divergent field names force command-specific parsing and increase the chance that action priority or target metadata is ignored.

## Workaround

Use only the `command` field, or maintain command-specific next action parsers.

## Candidate Fix

Standardize next action objects across commands. Use `kind`, `reason`, `target`, and `command` consistently. Preserve old fields temporarily as compatibility aliases if needed.

## Acceptance Criteria

- explain next_actions use the same schema as scan/status/verify.
- docs describe a single next_action schema.
- Tests validate schema consistency for representative commands.

## Evidence

- Observed during cycle 2 dogfooding while explaining `FIRE-9856EB644D66`.

# CFB-091: adding a later explicit atom changes the previous explicit atom hash

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | Atom Extraction / Explicit Atom Span |
| Observed while | adding `FrontierDriftReporter` in `algorithm-evolution-agent-lab` |

## Observation

When a new explicit `cf-atom` was added after existing explicit atoms in `frontier.py` and `test_frontier.py`, CodeFire reported `atom_changed` fires for the new drift reporter atoms, but also for existing atoms that were not semantically changed:

- `CODE-FrontierFeedbackIntegrator`
- `TEST-frontier-feedback-integrator-updates-frontier-signals`

This appears to happen because explicit atom content is hashed from the marker until the next explicit marker. A terminal or near-terminal explicit atom can therefore include trailing code. Adding a later marker shrinks or changes the previous atom span, so the previous atom hash changes even when its logical class/test did not.

## Reproduction

```bash
cd subprojects/algorithm-evolution-agent-lab
# Add a new explicit cf-atom after CODE-FrontierFeedbackIntegrator and after the feedback test atom.
codefire scan --path . --json
```

Observed changed atoms included:

```text
CODE-FrontierDriftReporter
CODE-FrontierFeedbackIntegrator
TEST-frontier-drift-reporter-summarizes-priority-shifts
TEST-frontier-feedback-integrator-updates-frontier-signals
```

The two feedback atoms were existing atoms from the prior commit and were pulled into the change set by span-boundary effects.

## Why It Matters

In docs-first development, adding one feature often adds a new class and a new test below the previous feature. If that causes the previous explicit atom to change, CodeFire creates extra fires and requires extra resolution/evidence for unaffected logic. This increases dogfood friction and makes the changed atom set less precise for AI tools.

## Workaround

Review the actual source diff manually and extinguish the extra fires with the same verification evidence when the existing atom was only affected by explicit span boundary changes.

## Candidate Fix

Make explicit `cf-atom` spans more stable. Possible approaches:

- support an explicit close marker;
- infer class/function/test block boundaries for common languages when the marker is adjacent to a symbol;
- record marker-to-next-marker span changes as a lower-severity boundary-change diagnostic;
- include span metadata in context so tools can see that an atom changed because its end boundary moved.

## Acceptance Criteria

- Adding a new explicit atom after an existing class/test marker does not change the previous atom hash when the previous symbol body is unchanged.
- If marker-to-next-marker span semantics remain, scan explains that the prior atom changed due to span boundary movement.
- Tests cover adding a later explicit atom below an existing terminal explicit atom.

## Evidence

- Observed on 2026-06-07 during `FrontierDriftReporter` dogfooding. `scan --path . --json --metrics` reported existing `CODE-FrontierFeedbackIntegrator` and `TEST-frontier-feedback-integrator-updates-frontier-signals` as changed alongside the new drift reporter atoms.

## Fix

Python explicit Atom extraction now detects the common docs-first marker pattern:

```python
# cf-atom: CODE-ExistingPolicy
class ExistingPolicy:
    ...
```

When the marker is followed by `class`, `def`, `async def`, or decorators for those symbols, the Atom hash span ends at the Python indent block boundary instead of the next `cf-atom` marker. If no Python symbol boundary can be inferred, CodeFire keeps the previous marker-to-next-marker behavior.

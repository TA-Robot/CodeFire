# CFB-092: extractor algorithm upgrades create mass atom_changed fires

## Summary

| Field | Value |
|---|---|
| Status | open |
| Severity | high |
| Type | migration |
| Area | Atom Extraction / Migration |
| Observed while | installing the CFB-091 Python explicit Atom span fix and scanning `algorithm-evolution-agent-lab` |

## Observation

After installing the CodeFire build that fixes Python explicit Atom spans, `algorithm-evolution-agent-lab` had no source change, but `codefire scan --path . --json --metrics` reported:

- `changed_atoms`: 102
- `open_fires`: 116

The changed atoms were broad Python code/test atoms such as `CODE-ArtifactCollectionContract`, `CODE-BenchmarkRegistry`, `CODE-FrontierDriftReporter`, and many `TEST-*` atoms. This was caused by the extractor intentionally changing the hashed content span from marker-to-next-marker to Python symbol block for common explicit Atom patterns.

## Why It Matters

This is not an application behavior change. It is a tool/extractor semantics change. CodeFire currently treats it like ordinary source edits, so the user must extinguish a large number of trace fires and attach evidence even though the project source was not modified.

For AI/tool operation, this creates several problems:

- large changed-atom sets drown out actual source changes;
- fire counts explode after a CodeFire upgrade;
- `context --changed` becomes noisy and expensive;
- the proper action is rebaseline/migration, not ordinary feature verification;
- users cannot distinguish "tool hash schema changed" from "the project changed".

## Reproduction

```bash
cd /workspace/project
./install.sh --prefix /home/devuser/.local
cd subprojects/algorithm-evolution-agent-lab
codefire scan --path . --json --metrics
```

Observed result after CFB-091 fix:

```text
changed_atoms: 102
open_fires: 116
```

## Candidate Fix

Add extractor/hash schema versioning and a migration-aware workflow:

- include extractor version and hash span strategy in AtomIndex metadata;
- when only extractor version changes and working files are unchanged, report `tool_migration_required` instead of ordinary `atom_changed` fire spam;
- add `codefire migrate atom-index --rebaseline` or `codefire commit --migration extractor` to seal the new AtomIndex after verification;
- include before/after extractor version in scan/verify/context JSON;
- provide a bulk resolution mode for migration-only fires when policy still requires explicit resolution;
- keep ordinary `atom_changed` behavior for actual source content changes.

## Acceptance Criteria

- Installing a CodeFire build with a new extractor/hash schema does not produce indistinguishable ordinary source-change fires for every affected Atom.
- `scan --json` identifies extractor/hash schema drift separately from source edits.
- A verified migration/rebaseline command can seal the new AtomIndex without manual per-fire rationale entry.
- Tests cover a fixture where working files are unchanged but extractor version changes.

## Evidence

- Observed on 2026-06-07 after installing the Python explicit Atom span fix for CFB-091.
- `codefire scan --path . --json --metrics` on `algorithm-evolution-agent-lab` reported 102 changed atoms and 116 open fires immediately after the tool upgrade.

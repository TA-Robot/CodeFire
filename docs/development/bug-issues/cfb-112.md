# CFB-112: process-style documentation IDs are extracted as CodeFire atoms

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | UX bug |
| Area | Atom extraction / Markdown documentation |
| Observed while | algorithm documentation doubling dogfood |

## Observation

While expanding `algorithm-evolution-agent-lab` documentation, a new process requirements document used Markdown headings such as:

```markdown
## REQ-PROC-001: Documentation Entry Point
## PROC-REQ-001: Documentation Entry Point
```

These headings were intended as local process-document section IDs, not CodeFire trace atoms. `codefire status --json` nevertheless reported `changed_atom_count: 160` for a docs-only branch. Renaming the headings to prose-style labels such as `Process Requirement 001` returned the branch to `changed_atom_count: 0` and non-Atom docs-only handling.

## Reproduction

```bash
cd /workspace/project/subprojects/algorithm-evolution-agent-lab
printf '## REQ-PROC-001: Documentation Entry Point\n\nText.\n' > docs/spec/tmp-process-ids.md
codefire status --path /workspace/project/subprojects/algorithm-evolution-agent-lab --json
```

The same behavior was observed with `PROC-REQ-001` style headings during the feature branch `feature/docs-full-doubling`.

## Why It Matters

Markdown documentation often uses requirement-like local IDs for process sections, checklists, or examples. If every all-caps hyphenated section ID is treated as a CodeFire atom, a docs-only change can look like a large Atom-bearing change set. That increases review noise, changes the status summary, and can push agents toward trace/fire workflows for headings that were never intended to participate in the CodeFire trace graph.

This is especially confusing in documentation-heavy work because the operator has to guess whether the IDs are legitimate trace atoms, accidental atoms, or merely non-Atom changed files.

## Workaround

Avoid `REQ-*`, `DES-*`, `CODE-*`, `TEST-*`, or similar all-caps hyphen-number heading IDs unless the document intentionally defines CodeFire atoms. Use prose labels such as `Process Requirement 001` for local section numbering.

## Candidate Fix

Tighten Markdown Atom extraction so accidental heading IDs are not treated as trace atoms unless they use an explicit supported marker or an allowlisted atom prefix. Possible approaches:

- require `# cf-atom:` for Markdown atoms outside known spec/design atom files;
- restrict implicit Markdown atoms to configured prefixes such as `REQ-AUTO-*`, `DES-AUTO-*`, `REQ-PRODUCT-*`, and existing project prefixes;
- add a diagnostic when a newly detected Markdown atom prefix is unknown or unlinked;
- document the implicit Markdown atom grammar and how to opt out.

## Acceptance Criteria

- A heading such as `## Process Requirement 001` is not an atom.
- A heading such as `## PROC-REQ-001: ...` is not an atom unless the project explicitly allows that prefix.
- Existing legitimate Markdown atoms continue to be extracted.
- `status --json` and `scan --json` expose accidental or unknown Markdown atom prefixes as warnings instead of silently treating them as large changed-atom sets.
- Tests cover accidental process-style headings in docs-only Markdown files.

## Evidence

- 2026-06-14, during `feature/docs-full-doubling`, `codefire status --path /workspace/project/subprojects/algorithm-evolution-agent-lab-feature-docs-full-doubling --json` reported `changed_atom_count: 160` after adding `REQ-PROC-*` / `PROC-REQ-*` headings.
- Renaming those headings to `Process Requirement 001` style changed the same branch back to `changed_atom_count: 0`, `non_atom_changed_file_count: 12`, and `open_fires: 0`.

# CFB-066: install can succeed while PATH still resolves an older CodeFire

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | medium |
| Type | ux |
| Area | Install / PATH precedence |
| Observed while | installing v0.9 Phase A help-routing fix |

## Observation

`./install.sh --prefix /home/devuser/.cargo` succeeded and installed `/home/devuser/.cargo/bin/codefire`, but `codefire` on PATH still resolved to `/home/devuser/.local/bin/codefire`. The subsequent smoke test used the older binary and reproduced the old `init --help` side effect.

## Reproduction

```bash
./install.sh --prefix /home/devuser/.cargo
which codefire
codefire init --help
```

If `~/.local/bin` precedes `~/.cargo/bin`, the active command can remain stale.

## Why It Matters

The improvement cycle depends on installing the just-built CodeFire before dogfooding algorithm changes. A successful install message is not enough if the shell still runs an older binary. This can create false negatives and accidental repository writes during smoke checks.

## Workaround

Install to the prefix that is first on PATH, or call the installed binary by absolute path. In this run, reinstalling with `./install.sh --prefix /home/devuser/.local` fixed the active command.

## Candidate Fix

After install, resolve `command -v codefire` and compare it with the installed target. If a different path wins, print a warning with the exact active path, installed path, and suggested prefix/PATH change. Optionally add `--verify-active` to fail when the installed binary is not the active binary.

## Acceptance Criteria

- install reports the active `codefire` path after installation.
- install warns or fails when the active path differs from the installed target.
- install smoke verifies the active binary's help/version fingerprint, not only the copied target.

## Evidence

- `which codefire` returned `/home/devuser/.local/bin/codefire` after installing to `/home/devuser/.cargo`.
- `/workspace/project/target/release/codefire-rs init --help` showed the fixed help text, while `codefire init --help` used the stale binary.
- Reinstalling to `/home/devuser/.local` made `codefire init --help`, `codefire open --help`, and `codefire request-merge --help` show usage without side effects.
- Reconfirmed during v1.0 Phase 1a on 2026-06-07: `./install.sh --prefix /home/devuser/.cargo` succeeded, but `which codefire` still returned `/home/devuser/.local/bin/codefire` and the active command still showed old `context/explain/migrate --help` behavior. Reinstalling with `./install.sh --prefix /home/devuser/.local` made `context --help`, `explain --help`, `migrate --help`, and `trace-graph --help` return usage text.
- Fixed by making `install.sh` report `active codefire: <path>` after install, verify active help/version when it matches the installed target, and warn when PATH resolves a different binary.
- Regression: `bash -n install.sh`; temp prefix install emitted PATH mismatch warning; `/home/devuser/.local` install emitted `active codefire verified`.

# CFB-132: Python extractor treats multiline string fixtures as declarations

## Summary

| Field | Value |
|---|---|
| Status | fixed |
| Severity | high |
| Type | correctness / compatibility |
| Area | Rust Python Atom extraction / hash schema |
| Observed while | creating the canonical Algorithm current-profile bridge with the final installed binary |

## Observation

The restored Rust Python derived-symbol extractor scans every physical line for `class`, `def`, or
`async def`. It does not track Python string state. Canonical
`tests/test_nameaudit.py` contains multiple triple-quoted source fixtures such as:

```python
src = """
class ExcessivelyLongClassName:
    def excessively_long_method(self):
        return 1
"""
```

Those fixture lines are incorrectly indexed as declarations in `test_nameaudit.py`. Repeated
fixtures therefore create duplicate derived IDs:

- `TEST:tests/test_nameaudit.py::class:ExcessivelyLongClassName`
- `TEST:tests/test_nameaudit.py::method:ExcessivelyLongClassName.excessively_long_method`

Installed `scan` reports zero source changes and zero Fires, but `verify` exits 13 with two blocking
`duplicate_atom_id` diagnostics. The branch head remains the legacy commit, so the real canonical
bridge cannot be sealed.

## Why It Matters

Derived Atom identity must describe executable/source declarations, not source-looking text inside
fixtures, documentation strings, or comments. False declarations can collide, distort trace
coverage, create false Fires, and block an otherwise unchanged repository. This also proves that the
provisional Python extractor semantics need a new hash-schema identity rather than a silent change.

## Workaround

Editing Algorithm fixtures to avoid declaration-looking strings would hide a CodeFire parser bug and
would make test readability worse. Explicit markers cannot remove the false derived declarations.

## Resolution

- Added a bounded linear Python lexical pass that masks single, continued, and triple-quoted string
  content and identifies real comment starts before symbol/block-boundary recognition.
- `cf-atom` is recognized only in actual comments outside strings. Original source lines remain the
  block-hash input and the constant-size marker ownership window is unchanged.
- Advanced the Atom hash schema from 3 to 4 because the same source bytes now produce the corrected
  derived Atom set.
- Kept the old sealed head intact and used normal `scan -> verify -> commit` to create a strict
  `sealed-snapshot-v1` child, rather than rewriting historical objects or Algorithm fixtures.

## Acceptance Criteria

- Declaration-looking text and `cf-atom` text inside single/triple strings are not extracted.
- Real class/top-level def/class-owned method IDs, explicit marker ownership, duplicate detection,
  and historical `ExperimentPlan` hash fixtures remain deterministic.
- Runtime remains linear in source bytes with bounded per-line/state memory.
- Source-unchanged old-schema scans are reported as tool migration with no ordinary Fire storm.
- Canonical Algorithm scan/verify/commit creates a strict current-profile bridge and ends
  `open-clean` with zero Fires.

# CodeFire v0.8 CFB Burn-down Plan

v0.8は、dogfoodingで登録した `CFB-*` issueをすべて解消するための開発計画である。issue単位で場当たり的に直すのではなく、共通原因ごとに実装をまとめ、同じCLI契約・状態算出・diagnostic生成を複数箇所へ重複実装しない。

## Scope

- 対象: `docs/development/bug-backlog.md` のopen CFB。
- 既にfixed: `CFB-001..CFB-004`, `CFB-019`。
- v0.8で解消するopen issue: `CFB-005..CFB-018`, `CFB-020..CFB-045`。
- 非対象: AI agent運用機能、agent marketplace、prompt orchestration。CodeFireは外部AIのための安定した管理ツールではあるが、AI agent運用自体は製品機能に入れない。

## Completion Criteria

- `bug-backlog.md` の全CFBが `fixed` になっている。
- 各 `docs/development/bug-issues/cfb-*.md` に、修正内容、テスト、確認コマンド、関連commitが追記されている。
- `cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace` が通る。
- installed `codefire` で `subprojects/algorithm-evolution-agent-lab` をdogfoodし、status/scan/verify/context/doctor/migrate/storage/evidence/show/list/branch/diff/commit dry-runのJSONが全て機械可読なenvelopeを返す。
- state labelと件数の矛盾が存在しない。不変条件として、open fire数が1以上なら `open-clean` / `open-consistent` を表示しない。

## Phase 0: Contract Before Fixes

Status: partially implemented.

Before touching individual bugs, add a v0.8 regression suite that captures the current dogfood failures. The suite should be split by behavior, not appended as one giant `tests.rs` block.

Test targets:

- `src/tests/cli_contract.rs`: JSON envelope, `--path`, subcommand help, show/list/branch/diff/commit dry-run JSON.
- `src/tests/state.rs`: status/scan/verify/commit state transition matrix.
- `src/tests/diagnostics.rs`: blocking-only data filtering, non-blocking trace completeness, non-Atom changed files.
- `src/tests/doctor_migrate.rs`: shared layout compatibility and repair next_actions.
- `src/tests/evidence.rs`: command failure, dry-run, captured output summary.
- `src/tests/fire_workflow.rs`: batch template generation, fire grouping, output summaries.

This phase closes no issue by itself. It prevents silent regressions while the shared implementation is changed.

## Phase 1: Command Surface Contract

Status: planned.

Implement a single command contract layer instead of letting each command parse/render independently.

Changes:

- Add a common path parser in `cli_model.rs` that accepts both positional path and `--path <path>` where the command operates on a local repo or open directory.
- Add a command registry or command metadata table in `main.rs` / `completion.rs` with command name, aliases, supported options, JSON support, help text, and path mode.
- Move JSON rendering through one `automation.rs` renderer that always emits `codefire.command_result.v1`, including failure paths.
- Add a `NextActionBuilder` in `automation.rs` that preserves the original path as both command text and machine-readable `target.path`.
- Make `context --changed --json` include scan-compatible `changed_atoms`, `open_fires`, `changed_count`, and `open_fire_count` at `data` top level while keeping existing nested context data backward compatible.
- Wrap `show --json`, `list --json`, `branch list --json`, `branch show --json`, and `diff --json` in the shared envelope.
- Ensure `diff` option flags match actual sections emitted. If impact payload is included by default, `options.impact` must be true or a separate `included_sections` field must explain the default.
- Ensure `commit --dry-run --json` returns `ok:false` envelope on verification blockers instead of plain text.

Expected issue closure: `CFB-023`, `CFB-024`, `CFB-026`, `CFB-029`, `CFB-040`, `CFB-041`, `CFB-042`, `CFB-043`, `CFB-044`, `CFB-045`.

Implemented so far:

- `status`, `scan`, `verify`, and `branch list` have broader `--path` handling where applicable.
- Major dogfooding commands now have direct subcommand help for `--help`.
- `branch list --json` now returns a command result envelope.

Remaining in this phase:

- `context --changed --json` scan-compatible top-level fields.
- `show --json`, `list --json`, `branch show --json`, `diff --json` envelope cleanup.
- `commit --dry-run --json` blocker envelope.
- path-preserving `next_actions`.
- structured JSON failure rendering.

## Phase 2: State Reducer and Open-Branch Invariants

Status: partially implemented.

Create a single state reducer and remove state naming from individual command flows.

Changes:

- Add `crates/codefire-cli/src/state.rs` with `OpenBranchSnapshot`, `OpenBranchState`, and `derive_open_state(snapshot)`.
- Inputs must include current base, active scan freshness, changed atom count, open fire count, stale resolution count, verify result, and pending commit status.
- Enforce these invariants:
  - `open_fires > 0` always means `open-burning`.
  - `changed_atoms == 0` and `open_fires == 0` means `open-clean` unless there is an explicit pending verification/commit state.
  - `verify` must not degrade `open-clean` to `open-consistent` when no worktree changes exist.
  - `status` must show whether scan data is stale or absent when it cannot predict current changed atoms.
- Replace `scan_branch_state()` and `status_state()` with calls into the reducer.
- Update `status --json` data with `state_reason`, `scan_freshness`, `last_scan_base`, and `open_fire_count`.

Expected issue closure: `CFB-010`, `CFB-012`, `CFB-014`, `CFB-015`, `CFB-016`.

## Phase 3: Diagnostic Filtering and Non-Atom Changes

Status: planned.

Make diagnostics policy-aware in both `diagnostics` and `data`, and expose non-Atom file changes explicitly.

Changes:

- In `automation.rs`, split verification data into `all_*` and `blocking_*` fields where policy can downgrade findings.
- For `verify --details --blocking-only --json`, ensure filtered views and `diagnostics` agree.
- In core scan, add a worktree file-change view comparing current materialized files with the base manifest.
- Add `non_atom_changed_files` and `non_atom_changed_count` to `scan --json`; add text empty states for both changed atoms and non-Atom files.
- Add policy support to warn or require fire/evidence for selected non-Atom paths later, but keep v0.8 default as warning/reporting only.

Expected issue closure: `CFB-006`, `CFB-013`, `CFB-017`, `CFB-028`.

## Phase 4: Fire Workflow Compression

Status: planned.

Reduce fire-resolution volume for docs-first and trace-heavy development.

Changes:

- Add `verify --batch-template` or `extinguish --batch-template` to generate limited YAML from current open fires.
- Add `--evidence-from-command` / `--evidence <id>` integration so one verified evidence can be attached to many related fires without hand-copying.
- Add `fire group` or `trace change set` planning that groups fires by changed requirement/design/code/test cluster and common evidence candidate.
- Add batch-oriented `next_actions` when more than one fire exists. Single-fire actions remain as secondary actions.
- Expand `extinguish` success output with display ID, stable UID, source atom, target atom, reason, resolution, and evidence summary.
- Expand `verify` success output with base commit, open fire count, stale resolution count, missing evidence count, blocking check count.
- Expand `commit` output with changed atom count, resolved fire count, non-Atom changed file count, evidence count, branch, base, and commit message.

Expected issue closure: `CFB-005`, `CFB-011`, `CFB-018`, `CFB-020`, `CFB-021`, `CFB-022`, `CFB-027`.

## Phase 5: Evidence Correctness

Status: planned.

Evidence capture must not silently turn failed commands into success-looking proof.

Changes:

- Add `--allow-failed-command` to `evidence add`; without it, non-zero command exit returns `ok:false` and does not create a normal evidence object.
- For failed command capture with explicit allowance, mark the evidence as failed-command evidence and emit warning diagnostics.
- Implement single-item `evidence add --dry-run --json`.
- Include captured stdout/stderr summaries, truncation flags, command exit code, timed-out flag, object path, artifact ref ID, and captured byte counts in `evidence_add_data_json`.
- Keep batch and single evidence paths on the same validation/result model.

Expected issue closure: `CFB-037`, `CFB-038`, `CFB-039`.

Implemented so far:

- single-item `evidence add --dry-run --json` returns a validated operation plan without writing objects or running the command.
- evidence add JSON/text result includes object path and bounded stdout/stderr summaries with truncation flags.

Remaining in this phase:

- `--allow-failed-command`.
- failed command evidence must be rejected or clearly marked by default.
- captured byte counts and batch/single result model cleanup.

## Phase 6: Doctor, Migrate, Storage, Metrics

Status: partially implemented.

Unify repository layout health and observability so commands do not contradict each other.

Changes:

- Create a shared layout definition used by `init`, `doctor`, `migrate`, and `storage`.
- Treat optional or auto-creatable directories as warnings or repairable issues, not repo-invalid blockers, when normal status/scan/verify/commit still work.
- Make `doctor` and `migrate check` use the same issue IDs, severities, planned actions, and compatibility vocabulary.
- Add `doctor --repair` or precise `migrate dry-run` / `migrate apply` next_actions for every repairable diagnostic.
- Support legacy `verification.required` policy YAML through a migration path: either compatible parse with deprecation warning or `migrate apply` rewrite.
- Make `storage [path] --json` an alias for `storage report [path] --json`, or remove/clarify the top-level help entry if only `storage report` is supported.
- Change unmeasured metrics phases to `null` in `phase_timings` or omit them from summary while preserving `phases[].measured=false`.
- Hide unimplemented cache fields by default, or move them under an explicit `experimental_unavailable` diagnostic until cache exists.
- Add a lightweight `perf` or `doctor --metrics` path that reports Atom count, object count, command phase timings, and large object warnings.

Expected issue closure: `CFB-007`, `CFB-008`, `CFB-025`, `CFB-030`, `CFB-031`, `CFB-032`, `CFB-033`, `CFB-034`, `CFB-035`, `CFB-036`.

Implemented so far:

- unmeasured metric phase timings are represented as `null`.
- unimplemented cache details are hidden behind `cache_status=unavailable`.
- `storage [path] [--json]` aliases `storage report ...`.

Remaining in this phase:

- shared layout definition for init/doctor/migrate/storage.
- doctor/migrate severity and planned-action vocabulary alignment.
- policy migration compatibility.
- perf/doctor metrics expansion.

## Phase 7: Module Boundary Cleanup

Status: planned.

Keep this work interleaved with the phases above. Do not defer it to the end, because many CFB fixes otherwise push more responsibility into `main.rs`.

Required moves:

- Keep `main.rs` as dispatch plus thin orchestration only.
- Put command contract helpers in `cli_model.rs` / `automation.rs`.
- Put state derivation in `state.rs`.
- Put repairable layout definitions in a shared module used by `doctor` and `migration`.
- Put test suites under `src/tests/<domain>.rs` rather than expanding the existing monolithic test file.

Expected issue closure: `CFB-009`.

# Documentation And Evidence Requirements

This specification records process-level requirements for documentation, evidence, branch workflow, and review artifacts.
The requirements are intentionally operational: they define what a contributor must leave behind so future work can be audited.

## Requirement Interpretation

- These requirements apply to documentation and research operations, not only Python source changes.
- A requirement is satisfied by current files, command output, or explicit records that another contributor can inspect.
- A passing unit test is useful evidence for behavior, but it does not replace experiment evidence or documentation evidence.
- A CodeFire warning can be nonblocking and still deserve review if it affects reader trust.

## Process Requirement 001: Documentation Entry Point

- Requirement: the project must provide a discoverable entry point before adding long-lived detail.
- Scope: this applies to documentation work and any feature branch that changes related files.
- Acceptance evidence: a reviewer can point to a file, command output, history row, or experiment note that proves the requirement.
- Minimum record: include objective, inputs, action taken, result, and next action when the requirement produces an artifact.
- Blocking condition: the requirement is not satisfied if the evidence exists only in chat, memory, or an uncommitted scratch file.
- Review method: inspect the nearest README, source atlas, operation guide, and CodeFire status before accepting completion.
- Regression risk: future contributors may repeat stale work, overclaim weak evidence, or edit the wrong module when this is missing.
- Related documentation: operations guides cover procedures; development docs cover history, roadmap, ownership, and audit state.
- Verification note: docs-only changes still need count checks, CodeFire verification, and the repository minimum test command unless explicitly waived.
